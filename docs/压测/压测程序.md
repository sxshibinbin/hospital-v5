# 背景
需要做一个压测程序，调用接口写入指定格式的数据，用来验证这个接口是否能扛的住压力。

# 压测指标
- 设备：4000台
- 不同设备比例：
    - GK8：25%
    - GS17：25%
    - 睡眠雷达：25%
    - 跌倒雷达：25%
- 发送频率（次/设备）：
    | 档位 | 事件速率 | 持续时间 | 目标 |
    |---|---:|---:|---|
    | 基准 | 15 events/s | 30 分钟 | 覆盖目标平均流量 |
    | 峰值 | 75 events/s | 20 分钟 | 覆盖 5 倍突发 |
    | 极限 | 150 events/s | 10 分钟 | 覆盖 10 倍突发和补报 |
- 持续时间：默认10分钟

- 说明：三类事件各自的发送频率是5分钟一次，但是实际测试过程中不可能是4000台设备5分钟同时发送三类事件，所以真实测试过程中以配置事件速率随机触发事件即可。

# 压测逻辑
- 针对压测指标要支持配置，可以是独立的配置文件，包括上报的接口地址。
- 根据设置的设备数量，生成设备字典信息包含：imei、iccid、longitude、latitude、site、conpanyName、contactList、mqPushType,elderList，其中：longitude、latitude、site、conpanyName、contactList、mqPushType,elderList都可以设置默认值，所有设备可一致，如："longitude": "112.48788123381752", "latitude": "37.860508982314", "site": "居然创客大厦","conpanyName": "三十天科技(山西)股份有限公司", "contactList": [{"name": "贾", "phonenumber": "13453100505", "contactType": 1}], "mqPushType": 1, "elderList": []；imei、iccid这两个属性每个设备要不一样，同一设备可一样。
- 不同设备类型上报说明
    - 设备类型：
        - 智能手环且设备版本：GK8
        不管什么事件，上报信息中要有"deviceType": "智能手环", "deviceVersion": "GK8"
            - 心跳类数据上报：上报数据中的"eventName"写"定位数据上报"，"dataType": 0，"deviceState": 0（其他值可参考\backend\logs\app_upload\20260727\04\upload_20260727_04_001.log）
            - 报警类数据上报：上报数据中的"eventName"写"报警测试"，"dataType": 2，"deviceState": 2（其他值可参考：GK8报警类数据上报）
            - 健康类数据上报：上报数据中的"eventName"写"健康数据上报"或"温度数据上报"或"计步和睡眠翻滚数据上报"，"dataType": 0，"deviceState": 0（其他值可参考\backend\logs\app_upload\20260727\07\upload_20260727_07_001.log）
        - 智能手环且设备版本：GS17
        不管什么事件，上报信息中要有"deviceType": "智能手环", "deviceVersion": "GS17"
            - 心跳类数据上报：上报数据中的"eventName"写"定位数据上报"，"dataType": 0，"deviceState": 0（其他值可参考\backend\logs\app_upload\20260727\04\upload_20260727_04_001.log）
            - 报警类数据上报：上报数据中的"eventName"写"报警测试"，"dataType": 2，"deviceState": 2（其他值可参考：GS17报警类数据上报）
            - 健康类数据上报：上报数据中的"eventName"写"健康数据上报"或"温度数据上报"或"计步和睡眠翻滚数据上报"，"dataType": 0，"deviceState": 0（其他值可参考\backend\logs\app_upload\20260727\07\upload_20260727_07_001.log）
        - 睡眠雷达且设备版本：SM-C03
        不管什么事件，上报信息中要有"deviceType": "睡眠雷达", "deviceVersion": "SM-C03"
            - 心跳类数据上报：上报数据中的"eventName"写"心跳"，"dataType": 0，"deviceState": 0（其他值可参考：睡眠雷达心跳类数据上报）
            - 报警类数据上报：上报数据中的"eventName"写"报警测试"，"dataType": 2，"deviceState": 2（其他值可参考：睡眠雷达报警类数据上报）
            - 健康类数据上报：上报数据中的"eventName"写"睡眠报告信息上报"，"dataType": 0，"deviceState": 0（其他值可参考：睡眠雷达健康类数据上报）
        - 跌倒雷达且设备版本：RT-C03AI
        不管什么事件，上报信息中要有"deviceType": "睡眠雷达", "deviceVersion": "RT-C03AI"
            - 心跳类数据上报：上报数据中的"eventName"写"心跳"，"dataType": 0，"deviceState": 0（其他值可参考：跌倒雷达心跳类数据上报）
            - 报警类数据上报：上报数据中的"eventName"写"报警测试"，"dataType": 2，"deviceState": 2（其他值可参考：跌倒雷达报警类数据上报）
            - 健康类数据上报：无
- 待验证程序的逻辑分两个环节：1、接收上报数据落文件；2、监控文件写数据库；
    压测程序新增监控线程/协程，每 5 秒采集：
      - 文件新增行数
      - iot_file_offsets 未完成文件数和未处理字节数
      - 新事件表/属性表新增行数
      - 停止发送后 backlog 清空耗时
- 上报是要求设备必须绑定用户，所以压测前的设备要先绑定用户才行
    压测程序启动前自动或手动初始化 iot_devices、iot_user_devices，并使用压测 IMEI 前缀，便于清理。否则很容易忘记初始化，HTTP 全 success，但不写文件，用户id默认1。
- signature / nonce / timestamp 不能复用样例值
     文档里的样例都是固定 signature。数据库事件表有 signature 去重，复用会走 ON CONFLICT DO NOTHING，压到的是去重逻辑，
     不是真实插入逻辑。每条事件都要生成唯一 signature、nonce、timestamp、signTime。
- 报警流量不要默认等同健康/心跳
     这对报警不真实。建议分场景：
      - 真实比例：心跳高、健康中、报警低
      - 健康高压：专门压指标写入和最新指标 upsert
      - 报警高压：专门压报警表
      - 混合峰值：按真实设备比例混合
- 报告指标需要更细
     建议补：
      - 请求成功/失败/超时数量
      - P50/P95/P99/max 延迟
      - 每秒发送数和每秒成功数
      - 后端 CPU、内存、磁盘 IO
      - PostgreSQL 连接数、慢 SQL、锁等待
      - 文件目录增长速度
      - 落库 TPS
      - backlog 最大值和清空耗时
      - 发送期间接口接收能力
      - 停止发送后后台追平能力
      - 这一点建议明确写到压测注意事项里。

# 压测注意事项
- 上报信息接收接口不能有阻塞。
- 测试完成后，针对接收接口的吞吐量，发送频率，发送总数，以及压测结果出个报告。
    - 报告里要有：
      - HTTP 成功率、P50/P95/P99 响应时间
      - 文件写入条数
      - iot_file_offsets backlog
      - 新表实际新增行数
      - 压测停止后多久能追平落库
- 压测程序尽量可以独立运行，避免和待压测程序混在一起。
- 压测程序代码存放路径D:\WorkSpace\WorkSpace_\hospital-v5\压测

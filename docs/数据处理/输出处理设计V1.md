针对你“**2000台设备、高频上报、平台超时限制、异步转储、海量日志**”的场景，直接给你结论：

**强烈建议采用“时间为主（按小时分区）+ 大小为辅（单文件上限触发滚动）”的拆分策略，并引入“双层目录结构”。**

绝对**不要**只按大小拆分（如 `log1.log, log2.log`），那样数据处理服务会因无法预判边界而丢数据或重复读。

下面是为你量身定制的详细落地方案。

### 1. 核心设计：分层目录 + 规律命名

为了保证数据处理服务（消费者）能够**零丢失、零重复**地找到文件，文件路径必须包含明确的时间语义，且文件名自带序号。

**推荐目录结构：**
```text
/logs/app_upload/
    └── dt=20260724/          # 按天分区（便于清理过期数据）
        └── hour=15/          # 按小时分区（消费者按小时拉取）
            ├── upload_20260724_15_001.log   # 15点第1个文件
            ├── upload_20260724_15_002.log   # 15点第2个文件（因大小触发了滚动）
            └── upload_20260724_15_003.log
    └── dt=20260724/hour=16/
            └── upload_20260724_16_001.log
```

### 2. 拆分逻辑的具体规则（写入服务）

写入服务（Producer）维护一个**当前活跃写入文件指针**，按以下规则滚动：

- **主触发条件（时间）**：**每小时整点强制滚动**。无论当前文件是否写满，到了 `HH:00:00`，立即关闭旧文件，新建 `新小时_001.log`。这保证了消费者可以按小时精准滑动窗口。
- **次触发条件（大小）**：**单文件达到 1GB 强制滚动**。如果还没到整点，但当前文件大小超过 1GB（例如每5秒上报1KB，2000台每小时约1.44GB，会触发滚动），则关闭当前文件，序号 `+1`（例如 `001` -> `002`）。
- **文件命名规律**：`{业务前缀}_{年月日}_{小时}_{三位序号}.log`。序号永远从 `001` 开始，单调递增且永不重复。

**伪代码逻辑：**
```python
def get_current_writer():
    now = datetime.now()
    hour_key = now.strftime("%Y%m%d_%H")
    # 检测是否跨小时 -> 重置序号为001
    if current_hour != hour_key:
        关闭当前文件，序号重置为 1
    # 检测文件大小 -> 序号+1
    if 当前文件大小 > 1GB:
        关闭当前文件，序号 += 1
    # 返回文件句柄：upload_{hour_key}_{seq:03d}.log
```

### 3. 数据处理服务（Consumer）如何“找对文件”而不丢数据？

数据处理服务不能靠“遍历所有文件”来找，那样会拿到正在写入的热文件（导致读不完整）。**核心机制是“偏移量状态管理 + 文件不可变等待”**。

- **约定规则**：写入服务写入文件时，使用 **`.tmp` 后缀**（如 `001.log.tmp`），当文件触发滚动（无论是因为满1G还是跨小时）被**关闭**时，立即**重命名**去掉 `.tmp` 后缀。
- **消费者拉取策略**：
  1. 维护一个 **Redis/DB 游标**，记录当前处理到的 `小时` 和 `文件序号`（例如：`{ "hour": "15", "seq": 2, "offset": 12345 }`）。
  2. 消费者定时（例如每30秒）扫描当前 `hour=15` 目录，**只检索**没有 `.tmp` 后缀且**修改时间（mtime）早于当前时间 5分钟** 的文件（确保该文件已被写服务彻底关闭，不再被追加）。
  3. 按文件名升序排序，从游标处继续读取。
  4. **处理完毕一条数据，必须立即记录该条数据在文件中的 `offset`（字节偏移量）**。即使服务重启，也能从上一次 `offset` 精确续读，保证 Exactly-Once（精确一次）。

### 4. 为什么按“小时”而不是“分钟”或“天”？

| 拆分维度 | 评估 |
| :--- | :--- |
| **按天** | 单文件太大（约 34GB/天），读写IO压力大，且断点续传粒度太粗，一旦报错重试代价极高。 |
| **按分钟** | 文件碎片化太严重（1440个/天），文件句柄频繁切换，操作系统 inode 压力大，且“跨分钟”的网络延迟会导致文件频繁滚动，性能差。 |
| **按小时（推荐）** | 每小时约 1.4GB，单文件适中；24个分区，消费者并发度灵活；跨小时边界清晰，天然适合做“T+1”或“实时滑动窗口”计算。 |

### 5. 针对“平台超时限制”的写入性能优化

为了把响应时间压缩到 **毫秒级**，**绝对不能**每次上报都 `flush` 刷盘。

- **不允许丢任何一条**，则需要开启 **AOF 机制**（即每收到一条先写操作系统的 Page Cache，设置 `write` 后立即返回，由操作系统异步刷盘，性能依然很高）。

### 6. 附加建议：如何应对数据处理服务“找不到文件”

你提到的“数据处理服务会找不到对应文件”，通常是由于**服务器时钟跳变**或**写入过程中异常崩溃**导致文件名跳跃。

- **解决方案**：写入服务在启动时，扫描当前小时目录，找到最大的 `seq` 序号，在此基础上 `+1` 继续写，**绝不覆盖已有文件**。
- **消费者“补偿扫描”机制**：如果消费者发现游标指向的 `hour=15` 目录不存在，不要报错退出，应该自动尝试 `hour=14` 或 `hour=16`，并检查是否存在未处理的 `seq`，最大程度保证数据连续性。

### 总结落地清单
1. **目录结构**：`dt=YYYYMMDD/hour=HH/`。
2. **滚动触发**：整点强制换文件 + 单文件超 1GB 滚动。
3. **原子性**：写入用 `.tmp`，关闭后重命名正式文件。
4. **消费者**：基于 Redis 记录 `(文件路径, offset)`，只读 5 分钟前的已关闭文件。
5. **性能**：异步批量刷盘（Buffer 攒批），响应时间控制在 5ms 以内。

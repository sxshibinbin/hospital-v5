# 日志管理详细设计

编写日期：2026-09-05  
适用范围：`admin_web` 后台管理系统、`backend` FastAPI 服务、健康档案与登录登出相关接口。

## 1. 背景与目标

当前系统已有基础审计能力：

- 后端存在 `audit_logs` 表，对部分管理员操作已有记录。
- `admin_web` 已有 `审计日志` 菜单和列表页，但仅查询最近 100 条，无检索条件、无分页。
- 健康档案接口 `backend/routers/profiles.py` 的新增、修改、删除暂未记录日志。
- 用户登录/登出接口 `backend/routers/auth.py` 暂未记录业务日志；后台前端 `logout()` 当前只清理本地 token，没有调用后端登出接口。

本次设计目标：

- 在 `admin_web` 增加或升级为“日志管理”菜单。
- 页面结构分为上下两部分：上方检索条件，下方日志表格列表。
- 日志列表支持分页查看。
- 健康档案新增、修改、删除记录日志。
- 用户登录、登出记录日志。
- 优先复用现有 `audit_logs` 体系，避免重复建设。

本阶段只输出设计和原型，不进行开发实现。

## 2. 菜单与页面设计

### 2.1 菜单位置

建议将现有菜单：

```text
审计日志 /audit
```

升级为：

```text
日志管理 /logs
```

兼容策略：

- 新增路由 `/logs`，页面组件建议命名为 `Logs.tsx`。
- 保留 `/audit` 路由重定向到 `/logs`，避免旧地址失效。
- 左侧菜单展示名称改为“日志管理”，图标沿用 `Activity` 或改用 `FileClock`。

### 2.2 页面布局

页面分为上下两个区域：

上方：检索条件区

- 时间范围：开始时间、结束时间。
- 日志类型：全部、登录登出、健康档案、后台管理、系统配置、高频问题、协议隐私。
- 操作类型：全部、登录、登出、新增、修改、删除、封禁/解封、发布、配置更新、密码修改。
- 操作结果：全部、成功、失败。
- 操作对象：全部、用户、健康档案、高频问题、系统配置、协议隐私。
- 操作人/用户：支持输入用户 ID、手机号后四位、管理员名称。
- 关键词：匹配日志详情、目标 ID、请求 ID。
- 按钮：查询、重置。

下方：日志表格区

- 显示当前查询结果。
- 支持分页：页码、上一页、下一页、每页条数。
- 建议默认每页 20 条，可选 10、20、50、100。

### 2.3 表格字段

| 列名 | 字段 | 说明 |
| --- | --- | --- |
| 时间 | `created_at` | 操作发生时间，按倒序展示 |
| 日志类型 | `module` | 例如：登录登出、健康档案、后台管理 |
| 操作类型 | `action` | 例如：login、logout、profile_create |
| 终端 | `terminal` | 例如：app、pc、admin_web |
| 结果 | `result` | success / failure |
| 操作人 | `actor_name` | 管理员名称、用户昵称或手机号脱敏 |
| 操作对象 | `target_type` + `target_id` | 例如：健康档案 #12 |
| IP | `ip_address` | 客户端 IP |
| 详情 | `details` | 简短摘要，敏感信息脱敏 |

建议提供“查看详情”按钮，打开侧边详情抽屉，展示完整日志上下文，包括请求 ID、User-Agent、变更字段等。

## 3. 数据模型设计

### 3.1 推荐方案

推荐复用现有 `audit_logs` 表，做兼容扩展。原因：

- 当前后台已有审计日志菜单、API、模型。
- 已经有部分管理员行为写入该表。
- 直接扩展可以保留历史数据，减少迁移风险。

### 3.2 现有字段

当前 `AuditLog` 模型字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | Integer | 主键 |
| `admin_id` | Integer | 管理员用户 ID |
| `action` | String(50) | 操作类型 |
| `target_id` | String(50) | 目标 ID |
| `details` | String(500) | 操作详情 |
| `created_at` | DateTime | 创建时间 |

### 3.3 建议扩展字段

| 字段 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| `actor_user_id` | Integer | 否 | 实际操作用户 ID，普通用户或管理员均可 |
| `actor_type` | String(20) | 是 | `admin` / `user` / `system` / `anonymous` |
| `actor_name` | String(100) | 否 | 冗余展示名称，避免用户后续改名影响日志 |
| `actor_phone_masked` | String(20) | 否 | 脱敏手机号，如 `138****1234` |
| `terminal` | String(20) | 是 | `app` / `pc` / `admin_web`，登录日志必须记录 |
| `module` | String(50) | 是 | `auth` / `profile` / `admin` / `question` / `agreement` / `setting` |
| `result` | String(20) | 是 | `success` / `failure` |
| `target_type` | String(50) | 否 | `user` / `patient_profile` / `question` / `system_config` |
| `ip_address` | String(64) | 否 | 请求 IP，优先取可信代理转发后的客户端 IP |
| `user_agent` | String(300) | 否 | 请求 User-Agent，超长截断 |
| `request_id` | String(64) | 否 | 请求链路 ID，没有则服务端生成 |
| `metadata_json` | Text | 否 | JSON 字符串，存放白名单扩展信息 |

兼容说明：

- `admin_id` 保留，旧管理员日志继续可读。
- 新增日志统一写 `actor_user_id`；管理员操作同时写 `admin_id` 和 `actor_user_id`。
- 旧字段 `details` 保留，作为表格摘要。
- `action` 保留，统一规范 action 枚举。

### 3.4 索引建议

| 索引 | 字段 | 用途 |
| --- | --- | --- |
| `idx_audit_logs_created_at` | `created_at` | 默认倒序分页 |
| `idx_audit_logs_module_created` | `module`, `created_at` | 按日志类型筛选 |
| `idx_audit_logs_action_created` | `action`, `created_at` | 按操作类型筛选 |
| `idx_audit_logs_result_created` | `result`, `created_at` | 按成功/失败筛选 |
| `idx_audit_logs_actor_user_id` | `actor_user_id` | 按用户追踪 |
| `idx_audit_logs_target` | `target_type`, `target_id` | 按对象追踪 |
| `idx_audit_logs_request_id` | `request_id` | 链路查询 |

## 4. 日志分类与枚举

### 4.1 日志类型

| module | 展示名称 | 来源 |
| --- | --- | --- |
| `auth` | 登录登出 | `backend/routers/auth.py` |
| `profile` | 健康档案 | `backend/routers/profiles.py` |
| `question` | 高频问题 | `backend/routers/admin.py` |
| `agreement` | 协议隐私 | `backend/routers/admin.py` |
| `setting` | 系统配置 | `backend/routers/admin.py` |
| `admin` | 后台管理 | 用户状态、密码等后台操作 |

### 4.2 操作类型

| action | 展示名称 | 记录时机 |
| --- | --- | --- |
| `login_password` | 密码登录 | `/api/auth/login` |
| `login_sms` | 短信登录 | `/api/auth/login/sms` |
| `login_carrier` | 一键登录 | `/api/auth/login/carrier` |

| `profile_create` | 新增健康档案 | `POST /api/profiles` |
| `profile_update` | 修改健康档案 | `PUT /api/profiles/{profile_id}` |
| `profile_delete` | 删除健康档案 | `DELETE /api/profiles/{profile_id}` |
| `update_user_status` | 用户状态更新 | 已有后台用户状态更新 |
| `create_question` | 新建高频问题 | 已有高频问题新增 |
| `update_question` | 更新高频问题 | 已有高频问题更新 |
| `delete_question` | 删除高频问题 | 已有高频问题删除 |
| `publish_question` | 发布高频问题 | 已有高频问题发布 |
| `update_agreement` | 更新协议隐私 | 已有协议更新 |
| `update_setting` | 更新系统配置 | 已有系统配置更新 |

### 4.3 操作结果

| result | 展示名称 | 说明 |
| --- | --- | --- |
| `success` | 成功 | 业务操作成功完成 |
| `failure` | 失败 | 登录失败、无权限、参数错误等需要审计的失败行为 |

## 5. 日志记录逻辑设计

### 5.1 统一日志工具

建议新增后端工具模块：

```text
backend/services/operation_log_service.py
```

核心方法：

```python
async def log_operation(
    db: AsyncSession,
    *,
    request: Request | None,
    actor_user: User | None,
    actor_type: str,
    module: str,
    action: str,
    result: str = "success",
    target_type: str | None = None,
    target_id: str | None = None,
    details: str | None = None,
    metadata: dict | None = None,
    commit: bool = False,
) -> None:
    ...
```

设计要求：

- 不在普通业务事务中强制 `commit`，默认只 `db.add()`，由业务接口统一提交。
- 对登录失败、鉴权失败等业务已中断场景，可提供 `log_operation_safe()` 使用独立 session 尝试写入，失败只写服务日志，不影响主流程。
- `request_id` 从请求头 `X-Request-ID` 获取，没有则生成。
- `ip_address` 从可信代理头和 `request.client.host` 获取；如果未配置可信代理，只使用 `request.client.host`。
- `metadata` 只允许白名单字段，不记录明文病史、过敏史、验证码、密码、token。

### 5.2 健康档案日志

健康档案属于敏感健康信息，日志只记录操作摘要和必要定位字段。

新增档案：

- 位置：`POST /api/profiles`
- action：`profile_create`
- actor：当前登录用户
- target：`patient_profile` + 新档案 ID
- details：`新增健康档案：本人/家人档案（姓名或关系标识）`
- metadata 建议只保留档案标识：

```json
{
  "profile_id": 31,
  "profile_name": "张三",
  "relation": "self"
}
```

修改档案：

- 位置：`PUT /api/profiles/{profile_id}`
- action：`profile_update`
- target：`patient_profile` + 档案 ID
- details：`修改健康档案：父亲-张三`
- metadata 只记录档案标识，不记录变更字段名、字段原文或差异内容。
- `medical_history`、`allergies` 等敏感字段不进入日志。

删除档案：

- 位置：`DELETE /api/profiles/{profile_id}`
- action：`profile_delete`
- target：`patient_profile` + 档案 ID
- details：`删除健康档案：母亲-李四`
- 删除前先读取档案摘要，删除后写日志。

### 5.3 用户登录日志

密码登录：

- 位置：`POST /api/auth/login`
- 成功 action：`login_password`，result：`success`
- 失败 action：`login_password`，result：`failure`
- details 示例：
  - 成功：`密码登录成功`
  - 失败：`密码登录失败：账号不存在/密码错误/账号锁定/账号已注销`
- terminal：`app`、`pc`、`admin_web`
- 终端来源建议由客户端登录入口携带并由后端兜底识别：
  - App 端固定记录 `app`
  - PC 端固定记录 `pc`
  - 后台管理登录固定记录 `admin_web`

短信登录：

- 位置：`POST /api/auth/login/sms`
- 成功 action：`login_sms`
- 失败 action：`login_sms`
- 失败原因建议分为：验证码无效、验证码过期、手机号格式错误。

一键登录：

- 位置：`POST /api/auth/login/carrier`
- 成功 action：`login_carrier`
- 失败 action：`login_carrier`
- 不记录运营商 token。

### 5.4 用户登出日志

后端：

- 位置：`POST /api/auth/logout`
- 当前逻辑已将 token 加入黑名单。
- 增加 action：`logout`，module：`auth`，result：`success`。

前端：

- `admin_web/src/api/index.ts` 中 `logout()` 当前只清理本地 token。
- 实现阶段建议先调用 `POST /api/auth/logout`，无论成功或失败，最后都清理本地 token 并跳转登录页。
- 移动端如已有登出入口，也建议同步调用后端登出接口。

- 仅管理员可访问。

请求参数：

| 参数 | 类型 | 必填 | 说明 |

| `page` | int | 否 | 默认 1 |

## 8. 安全与合规要求

日志是安全审计数据，设计阶段建议遵守以下规则：

- 不记录密码、验证码、token、运营商授权 token。
- 不记录健康档案中的病史、过敏史明文，也不记录字段变更内容。
- 手机号统一脱敏展示和存储：`138****1234`。
- 日志详情中的 metadata 采用白名单字段。
- 日志管理菜单仅管理员可访问。
- 日志记录失败不能导致用户核心业务失败，但必须写服务端错误日志。
- 日志表建议设置保留周期，默认保留 365 天；如后续接入等保要求，可按等级调整。

## 10. 验收标准

页面验收：

- 后台左侧出现“日志管理”菜单。
- 页面上方展示检索条件，下方展示日志表格。
- 支持按时间、日志类型、操作类型、操作结果、关键词检索。
- 支持分页、每页条数切换。
- 查询条件切换后数据正确刷新。

日志记录验收：

- 新增健康档案后出现 `profile_create` 成功日志，且可定位到具体档案。
- 修改健康档案后出现 `profile_update` 成功日志，且只显示档案标识。
- 删除健康档案后出现 `profile_delete` 成功日志，且只显示档案标识。
- 用户密码登录成功后出现 `login_password` 成功日志。
- 用户密码登录失败后出现 `login_password` 失败日志。
- 用户短信登录成功后出现 `login_sms` 成功日志。
- 用户一键登录成功后出现 `login_carrier` 成功日志。
- 用户登出后出现 `logout` 成功日志。
- 登录日志列表中可直接看出终端是 `app`、`pc` 还是 `admin_web`。
- 日志中不包含密码、验证码、token、病史、过敏史明文。

接口验收：

- `/api/admin/logs` 返回分页结构。
- `page`、`page_size`、筛选条件生效。
- 非管理员访问返回 403 或 401。
- 日志详情接口可查询单条日志。

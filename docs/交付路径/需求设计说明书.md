# 安小记 IoT 健康监测系统需求设计说明书

版本: V1.0  
编制日期: 2026-07-30  
输出目录: `docs\交付路径`

## 1. 文档概述

本文档依据 `docs` 目录下现有设计资料、接口对接说明、性能优化方案、压测程序设计以及后端现有实现整理，作为安小记移动端 IoT 健康监测能力的需求设计基线。

本文档覆盖:

- 移动端健康监测、报警记录、设备参数维护等业务需求。
- 后端接收 IoT 平台数据、落盘、批量入库、查询接口等服务需求。
- 性能、可靠性、安全、验收等非功能需求。

## 2. 项目背景

安小记移动应用需要接入 IoT 设备数据，向用户展示健康监测数据、设备状态、报警记录和趋势分析，并支持对设备参数进行维护。后端需要接收 IoT 平台推送的高频设备数据，在保证接收接口快速响应的同时，对数据进行异步解析、分类、入库和查询优化。

系统目标设备规模按 4000 台估算，设备类型包括:

| 设备类型 | 说明 | 规划占比 |
| --- | --- | --- |
| GK8 | 智能手表/健康监测设备 | 25% |
| GS17 | 智能手表/健康监测设备 | 25% |
| SM-C03 | 睡眠雷达 | 25% |
| RT-C03AI | 跌倒雷达 | 25% |

## 3. 建设目标

1. 支持用户绑定和查询 IoT 设备。
2. 支持健康监测首页展示设备状态、最新指标、报警数量等信息。
3. 支持单设备详情和指标趋势查询。
4. 支持设备报警记录查询和处理状态筛选。
5. 支持设备参数查询和下发，参数下发成功后保存本地配置。
6. 支持 IoT 平台通过订阅地址推送数据，后端快速返回，避免推送链路被数据库写入阻塞。
7. 支持文件落盘、偏移量记录、批量处理、断点续处理，降低数据丢失和重复处理风险。
8. 支持 4000 设备规模下的基准、峰值、极限压测验证。

## 4. 角色与系统对象

| 对象 | 说明 |
| --- | --- |
| 移动端用户 | 登录安小记 App，查看设备、健康指标、报警记录并维护设备参数。 |
| 后端接口服务 | 提供移动端接口、IoT 平台订阅接收接口、设备参数下发接口。 |
| IoT 平台 | 设备数据来源，向后端订阅地址推送设备事件，也接收设备查询和参数下发请求。 |
| 数据处理服务 | 监控上传日志文件，按批次解析数据并写入 PostgreSQL。 |
| 运维/测试人员 | 配置服务、打包 APK、执行压测、观察性能指标和日志。 |

## 5. 业务范围

### 5.1 范围内

- 用户登录后获取当前用户身份。
- 查询设备类型字典。
- 添加 IoT 设备并绑定用户。
- 查询用户绑定设备列表、最新健康指标和设备状态。
- 查询设备详情。
- 查询指标趋势。
- 查询报警记录。
- 查询和设置设备参数。
- 接收 IoT 平台 URL 校验和数据推送。
- IoT 原始数据落盘、批量解析入库。
- 压测数据构造、压测执行、指标采集和报告输出。
- Android APK 打包和后端地址配置。

### 5.2 范围外

- IoT 平台自身设备管理后台建设。
- 设备固件升级和远程诊断。
- 报警闭环处置流程的完整工单系统。
- 多租户权限体系扩展。
- 长周期数据仓库、离线报表和 BI 建设。

## 6. 总体业务流程

### 6.1 移动端查询流程

1. 用户通过手机号、短信或运营商方式登录。
2. 移动端保存 token，并通过当前用户信息获取 `userId`。
3. 健康监测页面根据当前用户查询绑定设备。
4. 后端从绑定关系、设备表、最新指标表和事件表聚合返回设备状态。
5. 用户进入设备详情后，可查询趋势数据、报警记录或参数设置。

### 6.2 IoT 数据接收流程

1. IoT 平台调用 `GET /api/iot/subscribe` 完成 URL 校验。
2. IoT 平台调用 `POST /api/iot/subscribe` 推送设备数据。
3. 后端校验设备是否已绑定。未绑定设备直接返回成功，不进入业务数据处理。
4. 已绑定设备的原始数据写入上传日志文件，接口快速返回 `success`。
5. 文件监控服务按文件成熟时间、偏移量和批次大小读取日志。
6. 数据处理服务解析事件，按健康、报警、心跳分类写入对应事件表和指标表。
7. 查询接口从最新指标表、分类事件表中读取数据，降低历史明细扫描压力。

## 7. 功能需求

| 编号 | 功能 | 需求说明 | 优先级 |
| --- | --- | --- | --- |
| FR-01 | 用户登录与当前用户 | 移动端应通过登录接口获取 token，通过当前用户信息确定 `userId`，不得在页面中固定写死用户 ID。 | 高 |
| FR-02 | 设备类型字典 | 系统应提供设备类型字典，供新增设备和页面筛选使用。 | 高 |
| FR-03 | 新增设备 | 用户输入 IMEI、设备类型、位置等信息后，后端调用 IoT 平台查询设备基础信息，成功后保存设备、联系人和用户绑定关系。 | 高 |
| FR-04 | 设备列表/健康监测 | 用户可查看已绑定设备列表、设备状态、最新心率、血氧、血压、体温、步数等指标。雷达设备应展示报警数量或对应状态信息。 | 高 |
| FR-05 | 设备详情 | 用户可查看单个设备的基础信息、最新上报时间、最新状态和指标摘要。 | 高 |
| FR-06 | 指标趋势 | 用户可按日、周、月、年查询指定指标趋势，后端应校验用户与设备绑定关系。 | 高 |
| FR-07 | 报警记录 | 用户可查询设备报警事件，支持按处理状态和时间范围筛选。未传时间范围时默认查询当天。 | 高 |
| FR-08 | 设备参数查询 | 用户可查询设备当前可维护参数和最近一次本地保存的参数值。 | 中 |
| FR-09 | 设备参数设置 | 用户可修改设备参数，后端调用 IoT 平台创建指令任务，全部成功后保存本地参数配置。 | 中 |
| FR-10 | IoT URL 校验 | 后端应支持 IoT 平台订阅地址校验，并按平台签名规则返回校验结果。 | 高 |
| FR-11 | IoT 数据接收 | 后端应快速接收平台推送数据，已绑定设备写入原始日志，未绑定设备返回成功但不落业务数据。 | 高 |
| FR-12 | 文件批量处理 | 系统应支持上传日志按成熟文件、偏移量、批量大小处理，异常后可从偏移量继续。 | 高 |
| FR-13 | 最新指标维护 | 健康指标入库时应维护 `iot_device_latest_metrics`，列表和详情优先读取最新指标表。 | 高 |
| FR-14 | 压测执行 | 系统应提供压测程序，支持模拟设备、并发推送、阶段化压测、统计 HTTP 与业务处理指标。 | 中 |
| FR-15 | APK 打包 | 系统应支持通过打包脚本生成 Android APK，并允许配置移动端访问的后端地址。 | 中 |

## 9. 数据需求

### 9.1 设备主数据

系统应保存设备 IMEI、ICCID、设备类型、设备型号、设备状态、经纬度、安装位置、房间名称、所属公司、启用时间等基础信息。

### 9.2 用户设备关系

系统应保存用户与设备绑定关系，支持一个用户绑定多台设备。查询设备列表、趋势、报警和参数时应基于绑定关系校验访问权限。

### 9.3 事件数据

系统应保存 IoT 平台上报的原始事件，并按业务类型拆分:

| 类型 | 判断规则 | 落库目标 |
| --- | --- | --- |
| 健康事件 | `eventName` 为健康、体温、计步睡眠等上报事件 | 健康事件表和健康事件指标表 |
| 报警事件 | `dataType = 2` 且 `deviceState = 2` | 报警事件表和报警事件指标表 |
| 心跳事件 | 不满足健康或报警规则的普通事件 | 心跳事件表和心跳事件指标表 |

同一条上报数据若同时满足健康和报警规则，应允许同时写入对应分类表。

### 9.4 最新指标

系统应维护设备维度、指标维度的最新指标值，支持列表页和详情页快速读取，减少从历史明细表中排序查询的压力。

### 9.5 参数数据

系统应保存设备参数编码、字段名、参数值、创建人、更新时间等信息。参数下发到 IoT 平台全部成功后，才更新本地参数表。

## 10. 设备参数需求

| 设备类型 | 参数范围 |
| --- | --- |
| GK8/GS17 | 心率采集间隔、体温采集间隔、计步开关、睡眠开始时间、睡眠结束时间、跌倒报警开关、跌倒灵敏度等。 |
| SM-C03 | 检测模式、心率开关、呼吸开关、睡眠开关、长时间无人计时开关、无人持续时长、异常挣扎开关、存在检测开关等。 |
| RT-C03AI | 有人报警开关、无人报警开关、跌倒高度等。 |

参数设置应按设备类型映射到 IoT 平台指令编码和字段名。平台指令创建失败时，后端应返回失败原因，不应写入本地参数配置。

## 11. 性能需求

### 11.1 压测规模

| 场景 | 事件速率 | 持续时间 | 说明 |
| --- | ---: | ---: | --- |
| 基准负载 | 15 events/s | 30 分钟 | 接近 4000 台设备每 5 分钟上报一次的平均压力。 |
| 峰值负载 | 75 events/s | 20 分钟 | 约 5 倍平均压力。 |
| 极限负载 | 150 events/s | 10 分钟 | 约 10 倍平均压力。 |

参考估算: 4000 台设备每 5 分钟上报一次，平均约 13.33 events/s。

### 11.2 关键性能指标

| 指标 | 要求 |
| --- | --- |
| 接收接口成功率 | 压测期间应保持稳定，失败需能定位到 HTTP、服务端或数据库处理阶段。 |
| 接收接口延迟 | 应统计 P50、P95、P99、最大值。 |
| 文件处理积压 | 压测完成后积压应可在可接受时间内清空。 |
| 数据库连接 | 连接数应保持在连接池容量和数据库限制范围内。 |
| 慢 SQL | 查询接口和批量入库不应出现持续性慢 SQL。 |
| 资源使用 | 应记录后端 CPU、内存、磁盘 IO、日志增长、数据库 TPS 等指标。 |

## 12. 可靠性需求

1. 接收接口不得依赖同步数据库写入完成后才返回。
2. 原始上传日志应按日期和小时目录落盘，支持文件滚动。
3. 文件处理应记录偏移量，服务重启后可继续处理未完成数据。
4. 批处理失败时应保留异常日志，并避免整批数据静默丢失。
5. 设备未绑定时应避免产生无效业务数据，同时向平台返回成功以减少平台重试压力。
6. 事件应通过签名等字段进行幂等控制，避免平台重试造成重复入库。

## 13. 安全需求

1. 移动端接口应使用登录 token 获取当前用户，不应依赖前端传入任意用户 ID 作为唯一鉴权依据。
2. 设备查询、趋势、报警和参数接口应校验用户设备绑定关系。
3. IoT 平台 URL 校验应按平台签名规则执行。
4. 平台账号、密钥、数据库密码等敏感配置应通过环境变量或配置文件管理，不应写入交付文档和客户端代码。
5. 参数下发接口应限制可下发参数范围，避免任意字段透传。

## 14. 验收标准

| 编号 | 验收项 | 验收标准 |
| --- | --- | --- |
| AC-01 | 登录用户 | 移动端能从当前登录态获取用户 ID，健康监测页面不依赖固定用户 ID。 |
| AC-02 | 设备新增 | 输入合法设备信息后可成功新增并绑定，重复绑定有明确提示。 |
| AC-03 | 健康监测列表 | 已绑定设备能展示基础信息、状态和最新指标，无数据时显示空状态。 |
| AC-04 | 指标趋势 | 日、周、月、年查询返回正确时间范围内的数据点。 |
| AC-05 | 报警记录 | 可按设备、时间、处理状态查询报警事件。 |
| AC-06 | 参数维护 | 参数查询和设置符合设备类型差异，平台下发失败不更新本地值。 |
| AC-07 | 数据接收 | IoT 平台推送数据时接口快速返回，已绑定设备数据可入库并被页面查询。 |
| AC-08 | 断点续处理 | 文件处理服务重启后可基于偏移量继续处理。 |
| AC-09 | 压测 | 基准、峰值、极限场景可输出完整指标报告。 |
| AC-10 | APK | 打包脚本可生成可安装 APK，手机访问后端地址配置正确。 |

## 15. 约束与风险

1. IoT 平台接口可用性会直接影响设备新增和参数下发成功率。
2. 趋势查询在月、年等长时间范围内依赖历史明细表索引，后续如数据量继续增长，应考虑汇总表或分区表。
3. 多实例部署时，本地文件落盘和文件监控需要明确实例目录、共享存储或消息队列方案。
4. 报警处置闭环尚未完整覆盖，后续如接入工单系统，需要扩展报警状态流转模型。
5. 参数字段映射依赖设备型号和平台协议，新增设备类型时需要同步维护映射表和测试用例。

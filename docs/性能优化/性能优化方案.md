# IoT 性能优化方案汇总

日期：2026-07-29

## 1. 背景与目标

当前预估规模：

- 设备数量：4000 台
- 上报频率：每台设备约 5 分钟 1 条
- 平均事件量：约 13.33 条/秒
- 每日事件量：约 1,152,000 条
- 指标属性表预计很快达到千万级，后续可能进入亿级

主要优化目标：

- 降低 `iot_event_items` 单表膨胀和文本数值转换带来的查询压力。
- 拆分报警、健康监测、心跳等不同业务价值和查询频率的数据。
- 避免设备当前状态读取需要跨多张历史事件表。
- 保证指标详情、报告页、设备在线状态查询都有稳定的数据路径。

## 2. 总体结论

不建议继续使用当前的 `iot_event_items(attr_value text)` 作为所有指标的长期主查询表。

也不建议简单改成一张健康大横表，因为当前指标不是同一次事件统一上报，心率、血氧、血压、温度、计步等指标有各自独立的上报时间。如果强行放到一张横表，会导致大量空字段、时间语义混乱，以及复杂的 upsert 拼接逻辑。

推荐方案是：

```text
原始层：保留原始事件，便于审计和回放
事件层：按业务类型拆分报警、心跳、健康事件
指标层：使用数值化纵向事实表存储指标
状态层：使用最新状态表和最新指标表支撑页面展示
汇总层：使用小时、天级汇总表支撑长周期趋势
```

核心原则：

- 历史明细查事实表。
- 当前状态查最新状态表。
- 报告页查最新指标表和统计表。
- 长周期趋势查汇总表。
- 心跳不污染健康指标和报警事件。

## 3. 指标数据建模

### 3.1 不采用健康大横表

大横表适合一条事件同时上报多个指标的场景，例如同一次采样同时包含心率、血氧、体温、血压。

当前业务前提是指标并不是同一次事件上报，因此大横表不合适：

- 不同指标的 `sign_time` 不一致。
- 单行无法准确表达采样时间。
- 大量字段为空。
- 后续需要复杂逻辑把多条事件拼成一行。
- 查询时容易把“同一时间窗口”误认为“同一次采样”。

### 3.2 推荐指标事实表

建议新增数值化纵向指标表：

```sql
CREATE TABLE iot_metric_samples (
  id BIGSERIAL PRIMARY KEY,
  device_id BIGINT,
  imei VARCHAR(64) NOT NULL,
  metric_code VARCHAR(64) NOT NULL,
  numeric_value DOUBLE PRECISION NOT NULL,
  raw_value VARCHAR(128),
  unit VARCHAR(32),
  sign_time TIMESTAMP NOT NULL,
  source_event_id BIGINT,
  created_at TIMESTAMP NOT NULL DEFAULT now()
);
```

典型 `metric_code`：

```text
heart_rate
spo2
systolic_pressure
diastolic_pressure
temperature
step_count
```

这个表解决的问题：

- `value` 直接数值化，查询时不再正则转换。
- 每个指标保留自己的真实采样时间。
- 指标详情接口可以复用统一查询逻辑。
- 新增指标不需要新增表。
- 可以按时间分区降低单表压力。

### 3.3 指标是否需要每个指标单独建表

可以作为后续扩展手段，但不建议第一阶段直接拆成很多物理表。

优先顺序建议：

1. 先使用 `iot_metric_samples` 数值化纵表。
2. 对 `iot_metric_samples` 按 `sign_time` 做分区。
3. 如果某些指标量特别大，再考虑按 `metric_code` 二级分区。
4. 只有单个指标明显成为独立瓶颈时，再拆物理表。

如果未来确实需要物理拆表，也建议保持统一查询入口。例如：

```text
iot_metric_heart_rate_samples
iot_metric_spo2_samples
iot_metric_temperature_samples
iot_metric_step_samples
```

但业务代码不应到处拼表名，应通过统一 repository 或视图封装。

## 4. 事件表拆分方案

当前 `iot_device_events` 混合存储报警、健康监测、心跳等事件。长期看不利于查询、归档和索引维护。

建议拆分为：

```text
iot_raw_events            原始事件归档，可选入库，也可文件归档
iot_health_events         健康相关事件头信息
iot_alarm_events          报警事件
iot_heartbeat_events      心跳事件
```

### 4.1 健康事件

健康事件主要用于关联指标来源和审计，不一定承担指标详情查询。

指标详情应优先查 `iot_metric_samples`，而不是从事件 JSON 或原 `iot_event_items` 中解析。

### 4.2 报警事件

报警数据价值高、查询频率相对高，但数据量通常远小于心跳和健康指标。

建议独立表：

```sql
CREATE TABLE iot_alarm_events (
  id BIGSERIAL PRIMARY KEY,
  device_id BIGINT,
  imei VARCHAR(64) NOT NULL,
  alarm_type VARCHAR(64),
  alarm_level VARCHAR(32),
  alarm_content TEXT,
  sign_time TIMESTAMP NOT NULL,
  status SMALLINT NOT NULL DEFAULT 1,
  source_event_id BIGINT,
  created_at TIMESTAMP NOT NULL DEFAULT now()
);
```

常用索引：

```sql
CREATE INDEX idx_alarm_imei_time
  ON iot_alarm_events (imei, sign_time DESC);

CREATE INDEX idx_alarm_type_time
  ON iot_alarm_events (alarm_type, sign_time DESC);

CREATE INDEX idx_alarm_unresolved
  ON iot_alarm_events (imei, sign_time DESC)
  WHERE status = 1;
```

### 4.3 心跳事件

心跳数据量大，但日常查询价值低，主要用于判断设备是否在线。

建议策略：

- 心跳明细单独存 `iot_heartbeat_events`。
- 明细只保留短周期，例如 7-30 天。
- 长周期只保留小时或天级统计。
- 设备是否在线不直接扫心跳表，而是查 Redis 或最新状态表。

示例表：

```sql
CREATE TABLE iot_heartbeat_events (
  id BIGSERIAL PRIMARY KEY,
  device_id BIGINT,
  imei VARCHAR(64) NOT NULL,
  heartbeat_time TIMESTAMP NOT NULL,
  battery_level DOUBLE PRECISION,
  signal_strength DOUBLE PRECISION,
  device_status VARCHAR(64),
  created_at TIMESTAMP NOT NULL DEFAULT now()
);
```

## 5. 设备当前状态方案

事件表拆分后，不应通过查询多张历史表来拼设备当前状态。

推荐新增状态投影表：

```sql
CREATE TABLE iot_device_latest_state (
  device_id BIGINT PRIMARY KEY,
  imei VARCHAR(64) NOT NULL UNIQUE,
  online_status SMALLINT NOT NULL DEFAULT 0,
  last_event_time TIMESTAMP,
  last_heartbeat_time TIMESTAMP,
  last_health_time TIMESTAMP,
  last_alarm_time TIMESTAMP,
  battery_level DOUBLE PRECISION,
  signal_strength DOUBLE PRECISION,
  device_status VARCHAR(64),
  location VARCHAR(255),
  updated_at TIMESTAMP NOT NULL DEFAULT now()
);
```

前端读取设备状态时，只查这张表，不查历史事件表。

### 5.1 在线状态

在线状态建议优先使用 Redis TTL：

```text
key: iot:device:online:{imei}
ttl: 10 分钟或按设备上报周期配置
```

判断逻辑：

- Redis key 存在：在线。
- Redis key 不存在：离线或未知。
- 数据库 `iot_device_latest_state.last_heartbeat_time` 作为兜底。

这样可以避免每条心跳都变成一次强依赖数据库查询。

### 5.2 状态更新频率

每次事件都带设备状态时，不建议无脑全字段 update。

建议策略：

- 只更新本次事件涉及的字段。
- 状态值没有变化时，尽量减少历史写入。
- 心跳只更新 `last_heartbeat_time`、电量、信号等必要字段。
- 设备状态变化时，额外写入状态历史表。
- 高频字段可以做节流，例如同一设备 1 分钟内只更新一次非关键状态。

状态历史表可选：

```sql
CREATE TABLE iot_device_status_history (
  id BIGSERIAL PRIMARY KEY,
  device_id BIGINT,
  imei VARCHAR(64) NOT NULL,
  field_name VARCHAR(64) NOT NULL,
  old_value VARCHAR(255),
  new_value VARCHAR(255),
  changed_at TIMESTAMP NOT NULL,
  source_event_id BIGINT
);
```

## 6. 最新指标表

报告页需要展示最新心率、血氧、血压、温度、计步等，不应实时扫描千万级历史表。

建议新增：

```sql
CREATE TABLE iot_device_latest_metrics (
  imei VARCHAR(64) NOT NULL,
  metric_code VARCHAR(64) NOT NULL,
  numeric_value DOUBLE PRECISION NOT NULL,
  raw_value VARCHAR(128),
  unit VARCHAR(32),
  sign_time TIMESTAMP NOT NULL,
  updated_at TIMESTAMP NOT NULL DEFAULT now(),
  PRIMARY KEY (imei, metric_code)
);
```

每次某个指标上报后，只 upsert 对应的 `(imei, metric_code)`。

报告页查询路径：

```text
用户绑定设备
  -> iot_device_latest_state
  -> iot_device_latest_metrics
  -> iot_alarm_daily_stats 或 iot_alarm_events 今日统计
```

这样报告页不需要从 `iot_metric_samples` 中做 `DISTINCT ON` 取最新值。

## 7. 汇总表方案

指标详情短周期可以查原始指标表，长周期应该查汇总表。

建议新增小时汇总：

```sql
CREATE TABLE iot_metric_hourly_stats (
  imei VARCHAR(64) NOT NULL,
  metric_code VARCHAR(64) NOT NULL,
  bucket_time TIMESTAMP NOT NULL,
  min_value DOUBLE PRECISION,
  max_value DOUBLE PRECISION,
  avg_value DOUBLE PRECISION,
  sample_count BIGINT NOT NULL,
  PRIMARY KEY (imei, metric_code, bucket_time)
);
```

建议新增天汇总：

```sql
CREATE TABLE iot_metric_daily_stats (
  imei VARCHAR(64) NOT NULL,
  metric_code VARCHAR(64) NOT NULL,
  stat_date DATE NOT NULL,
  min_value DOUBLE PRECISION,
  max_value DOUBLE PRECISION,
  avg_value DOUBLE PRECISION,
  sample_count BIGINT NOT NULL,
  PRIMARY KEY (imei, metric_code, stat_date)
);
```

查询建议：

| 时间范围 | 查询来源 |
|---|---|
| 最近 24 小时 | `iot_metric_samples` |
| 最近 7 天 | `iot_metric_samples` 或小时汇总 |
| 最近 30-90 天 | 小时汇总 |
| 90 天以上 | 天汇总 |

## 8. 分区与索引

### 8.1 分区建议

`iot_metric_samples` 数据增长最快，必须分区。

如果按每条事件 6 个属性估算：

- 每天约 691 万行。
- 每月约 2.07 亿行。

建议：

- 第一阶段按周分区，单分区约 4800 万行。
- 如果实际属性数较少，可先按月分区。
- 后续根据热点指标考虑二级分区或独立物理表。

`iot_heartbeat_events` 也建议按时间分区，因为它只需要短周期保留，分区删除比逐行删除更稳定。

### 8.2 核心索引

指标明细：

```sql
CREATE INDEX idx_metric_imei_code_time
  ON iot_metric_samples (imei, metric_code, sign_time DESC);

CREATE INDEX idx_metric_code_time
  ON iot_metric_samples (metric_code, sign_time DESC);
```

最新指标：

```sql
PRIMARY KEY (imei, metric_code)
```

最新状态：

```sql
CREATE UNIQUE INDEX idx_latest_state_imei
  ON iot_device_latest_state (imei);
```

心跳：

```sql
CREATE INDEX idx_heartbeat_imei_time
  ON iot_heartbeat_events (imei, heartbeat_time DESC);
```

报警：

```sql
CREATE INDEX idx_alarm_imei_time
  ON iot_alarm_events (imei, sign_time DESC);
```

## 9. 写入链路

推荐写入流程：

```text
设备平台上报
  -> /api/iot/subscribe
  -> 原始事件落文件或队列
  -> 后台批量解析
  -> 按事件类型路由
  -> 批量写入指标、报警、心跳表
  -> 更新最新状态表和最新指标表
  -> 异步刷新小时、天汇总
```

关键要求：

- 使用数据库连接池。
- 文件或队列消费按批处理，例如 200-1000 条一批。
- `iot_metric_samples` 批量 insert。
- checkpoint 按批更新。
- 解析失败进入死信文件或死信表。
- 状态表和最新指标表使用 upsert。

## 10. 读取链路

### 10.1 指标详情

```text
短周期：
用户 -> 设备绑定校验 -> iot_metric_samples

长周期：
用户 -> 设备绑定校验 -> iot_metric_hourly_stats / iot_metric_daily_stats
```

不再从 `iot_event_items.attr_value` 正则转换。

### 10.2 健康监测报告页

```text
用户绑定设备
  -> iot_device_latest_state
  -> iot_device_latest_metrics
  -> 今日报警统计
```

不再对历史明细表做实时最新值扫描。

### 10.3 设备在线状态

```text
优先 Redis TTL
  -> 兜底 iot_device_latest_state.last_heartbeat_time
```

不直接查 `iot_heartbeat_events`。

## 11. 与现有表的关系

现有表可以这样处理：

| 当前表 | 后续定位 |
|---|---|
| `iot_device_events` | 短期兼容；后续作为原始事件或逐步拆分 |
| `iot_event_items` | 短期兼容；后续迁移到 `iot_metric_samples` |
| `iot_devices` | 继续作为设备基础档案表 |
| `iot_user_devices` | 继续作为用户设备绑定表 |

建议迁移期间保留双写：

```text
旧表继续写入，保证现有接口不受影响
新表同步写入，用于新查询接口验证
验证通过后，读接口切换到新表
最后再考虑停止旧表写入或降级为归档
```

## 12. 落地顺序

### 第一阶段：优先解决查询 CPU 和写入瓶颈

- 新增 `iot_metric_samples`。
- 落库时把指标值解析为 `numeric_value`。
- 指标详情接口切换到 `iot_metric_samples`。
- 后台消费改为批量落库。
- 引入数据库连接池。

### 第二阶段：拆事件类型

- 新增 `iot_alarm_events`。
- 新增 `iot_heartbeat_events`。
- 心跳数据设置短周期保留策略。
- 报警查询切换到报警表。

### 第三阶段：状态和报告页优化

- 新增 `iot_device_latest_state`。
- 新增 `iot_device_latest_metrics`。
- 报告页读取最新状态和最新指标。
- 在线状态接入 Redis TTL。

### 第四阶段：分区和汇总

- `iot_metric_samples` 按时间分区。
- `iot_heartbeat_events` 按时间分区。
- 新增小时、天级汇总表。
- 长周期趋势查询切换到汇总表。

## 13. 最终推荐架构

```text
写入：
subscribe -> raw file/queue -> batch parser -> typed tables -> latest/cache/stats

历史指标：
iot_metric_samples

报警：
iot_alarm_events

心跳：
iot_heartbeat_events + Redis TTL + latest_state

当前设备状态：
iot_device_latest_state

最新健康指标：
iot_device_latest_metrics

趋势汇总：
iot_metric_hourly_stats
iot_metric_daily_stats
```

该方案兼顾了：

- 指标不是同一次上报的事实。
- 千万级明细数据的查询性能。
- 心跳、报警、健康数据的不同生命周期。
- 前端报告页和设备状态页的读取效率。
- 后续横向扩展和历史归档。

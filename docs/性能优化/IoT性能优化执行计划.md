# IoT 性能优化执行计划

日期：2026-07-29

## 1. 执行原则

本次优化不建议一次性替换现有链路，推荐采用：

```text
先新增表结构
再新旧双写
再数据对账
再灰度切读
最后旧表降级
```

核心原则：

- 不直接删除旧表。
- 不一次性切换全部接口。
- 不让前端感知底层表结构变化。
- 先保证数据一致性，再优化查询性能。
- 写入链路优先保证可补偿、可追踪、可回放。

## 2. 阶段 0：基线确认

### 2.1 目标

明确当前数据来源、事件类型、指标字典、性能现状和数据保留策略。

### 2.2 任务

- 梳理平台上报事件类型。
- 确认健康监测、报警、心跳分别对应哪些 `dataType` 或业务字段。
- 整理指标字典。
- 统计当前接口性能。
- 统计当前数据增长速度。
- 明确历史数据保留周期。

### 2.3 指标字典内容

至少包含：

| 字段 | 说明 |
|---|---|
| `metric_code` | 系统内部指标编码 |
| 平台原始字段名 | 平台上报字段 |
| 中文名称 | 前端展示名称 |
| 单位 | bpm、%、mmHg、摄氏度、步等 |
| 数值类型 | 整数、浮点 |
| 正常范围 | 用于校验和告警 |
| 是否参与趋势 | 是否需要指标详情 |
| 是否参与报告页 | 是否需要最新值 |

### 2.4 产出

```text
事件类型映射表
指标字典
当前性能基线
数据保留策略
```

### 2.5 验收标准

- 能准确区分健康监测、报警、心跳事件。
- 所有前端需要展示和统计的指标都有明确 `metric_code`。
- 当前上报、落库、查询耗时有可对比基线。

## 3. 阶段 1：新增表结构

### 3.1 目标

新增性能优化所需的数据模型，但不影响现有业务读写。

### 3.2 新增表

```text
iot_metric_samples          数值化指标明细
iot_alarm_events            报警事件
iot_heartbeat_events        心跳事件
iot_device_latest_state     设备最新状态
iot_device_latest_metrics   设备最新指标
iot_metric_hourly_stats     小时汇总
iot_metric_daily_stats      天汇总
```

### 3.3 关键设计

`iot_metric_samples` 使用纵向模型：

```text
imei + metric_code + numeric_value + sign_time
```

不使用健康大横表，因为不同指标不是同一次事件上报。

`iot_device_latest_metrics` 使用：

```text
primary key (imei, metric_code)
```

每次只更新当前上报指标的最新值。

`iot_device_latest_state` 保存设备当前状态，前端读取状态时不跨多张历史表查询。

### 3.4 产出

```text
数据库迁移脚本
索引脚本
表结构说明
回滚脚本
```

### 3.5 验收标准

- 新表可独立创建。
- 不影响现有 `iot_device_events`、`iot_event_items` 读写。
- 核心索引创建完成。
- 回滚脚本可用。

## 4. 阶段 2：写入链路双写

### 4.1 目标

现有旧表继续写入，同时按新模型写入新表，为后续切读做准备。

### 4.2 写入路由

```text
健康指标 -> iot_metric_samples
报警事件 -> iot_alarm_events
心跳事件 -> iot_heartbeat_events
设备状态 -> iot_device_latest_state
最新指标 -> iot_device_latest_metrics
```

### 4.3 任务

- 增加事件分类逻辑。
- 增加指标解析逻辑。
- 把文本指标值解析为 `numeric_value`。
- 对健康指标写入 `iot_metric_samples`。
- 对报警事件写入 `iot_alarm_events`。
- 对心跳事件写入 `iot_heartbeat_events`。
- 对最新指标执行 upsert。
- 对设备最新状态执行 upsert。
- 增加解析失败记录。
- 增加新旧表对账脚本。

### 4.4 状态更新规则

- 每次事件只更新本次携带的状态字段。
- 高频心跳不写状态历史。
- 状态值变化时，可写入状态历史表。
- `last_event_time` 可以随事件推进。
- `last_heartbeat_time` 只由心跳事件推进。
- `last_health_time` 只由健康事件推进。
- `last_alarm_time` 只由报警事件推进。

### 4.5 产出

```text
新旧双写代码
事件分类器
指标解析器
解析失败日志或死信表
新旧数据对账脚本
```

### 4.6 验收标准

- 旧表写入不受影响。
- 新表数据能按事件类型正确落库。
- 指标数值解析准确。
- 最新指标表只保留每个设备每个指标最新值。
- 最新状态表能反映设备最近状态。
- 对账结果可解释。

## 5. 阶段 3：写入性能优化

### 5.1 目标

解决逐行建连、逐行 checkpoint、逐条 insert 的写入瓶颈。

### 5.2 任务

- 引入 IoT 数据库连接池。
- 文件监听消费改为批处理。
- 每批建议 200-1000 条事件。
- `iot_metric_samples` 使用批量 insert。
- 事件表、报警表、心跳表按批写入。
- checkpoint 按批更新。
- 增加失败事件死信处理。
- 增加落库延迟监控。

### 5.3 推荐写入流程

```text
subscribe 接收
  -> 原始事件写文件或队列
  -> 后台批量读取
  -> 批量解析
  -> 批量写事实表
  -> 批量更新 checkpoint
  -> upsert 最新状态和最新指标
```

### 5.4 产出

```text
连接池实现
批量消费逻辑
批量写入逻辑
checkpoint 批量更新逻辑
死信处理逻辑
落库监控指标
```

### 5.5 验收标准

| 场景 | 验收标准 |
|---|---|
| 正常流量 | 15 events/s 稳定无积压 |
| 5 倍突发 | 75 events/s 可持续处理 |
| 10 倍突发 | 150 events/s 不丢数据，可追平 |
| 落库延迟 | 正常情况下小于 30 秒 |
| 死信处理 | 单条坏数据不阻塞整批 |

## 6. 阶段 4：查询接口切换

### 6.1 目标

将高频查询从旧大表切换到新表，降低查询 CPU 和大表扫描压力。

### 6.2 切换顺序

建议按接口逐步切换：

```text
1. 指标详情接口
2. 健康监测报告页最新指标
3. 设备在线状态
4. 报警查询
```

### 6.3 指标详情接口

旧路径：

```text
iot_event_items.attr_value
  -> 正则转换 numeric
  -> 按时间聚合
```

新路径：

```text
iot_metric_samples.numeric_value
  -> 直接按时间聚合
```

### 6.4 报告页

旧路径：

```text
从历史明细表 DISTINCT ON 取最新值
```

新路径：

```text
iot_device_latest_metrics
iot_device_latest_state
今日报警统计
```

### 6.5 在线状态

新路径：

```text
优先 Redis TTL
兜底 iot_device_latest_state.last_heartbeat_time
```

不直接扫描心跳历史表。

### 6.6 产出

```text
指标详情接口新查询实现
报告页新查询实现
设备状态新查询实现
报警查询新查询实现
灰度开关
结果对账脚本
```

### 6.7 验收标准

| 接口 | 验收标准 |
|---|---|
| 指标详情 7 天范围 | p95 小于 800 ms |
| 指标详情 30 天范围 | p95 小于 1.5 s |
| 报告页 1000 台设备 | p95 小于 1 s |
| 在线状态 | 不依赖历史心跳表扫描 |
| 查询结果 | 与旧表对账一致或差异可解释 |

## 7. 阶段 5：分区与汇总

### 7.1 目标

支撑 `iot_metric_samples` 千万级、亿级数据规模。

### 7.2 分区策略

`iot_metric_samples`：

- 优先按 `sign_time` 分区。
- 若每月超过 2 亿行，建议按周分区。
- 如后续单个指标过大，再考虑按 `metric_code` 二级分区。

`iot_heartbeat_events`：

- 按时间分区。
- 使用分区删除完成过期数据清理。

### 7.3 汇总策略

新增：

```text
iot_metric_hourly_stats
iot_metric_daily_stats
```

查询策略：

| 时间范围 | 查询来源 |
|---|---|
| 24 小时内 | `iot_metric_samples` |
| 7 天内 | `iot_metric_samples` 或小时汇总 |
| 30-90 天 | 小时汇总 |
| 90 天以上 | 天汇总 |

### 7.4 产出

```text
分区表迁移脚本
分区创建任务
历史数据迁移任务
小时汇总任务
天汇总任务
过期分区清理任务
```

### 7.5 验收标准

- 千万级数据下核心查询仍走目标索引或目标分区。
- 长周期趋势不直接扫描全量原始明细。
- 过期心跳数据可通过分区快速清理。
- 分区维护任务可自动执行。

## 8. 阶段 6：旧表降级

### 8.1 目标

新链路稳定后，旧表不再承担核心查询压力。

### 8.2 处理策略

`iot_device_events`：

- 短期保留兼容。
- 后续可降级为原始事件或事件索引表。

`iot_event_items`：

- 停止作为指标详情主查询表。
- 可保留一段时间用于对账。
- 后续根据保留策略归档或停止写入。

### 8.3 产出

```text
旧表降级方案
旧接口兼容策略
历史数据归档策略
停止双写计划
```

### 8.4 验收标准

- 所有核心查询已切换到新表。
- 新旧数据对账通过。
- 旧表停止承担高频查询。
- 旧表归档或保留策略明确。

## 10. 优先级汇总

### P0

- 指标字典和事件类型确认。
- 新增 `iot_metric_samples`。
- 数值化指标写入。
- 指标详情接口切换。
- 数据库连接池。
- 批量落库。

### P1

- 新增 `iot_device_latest_metrics`。
- 新增 `iot_device_latest_state`。
- 报告页切换最新表。
- 心跳数据拆表。
- 在线状态 Redis TTL。

### P2

- 报警事件拆表。
- 小时汇总表。
- 天汇总表。
- 分区表。
- 旧表降级和归档。

## 11. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 新旧双写数据不一致 | 增加对账脚本，按 imei、metric_code、sign_time 校验 |
| 指标解析失败 | 记录死信数据，保留原始 payload |
| 批量落库部分失败 | 单批事务控制，失败批进入重试或死信 |
| 查询切换后结果差异 | 接口灰度，双查对比 |
| 分区迁移影响线上 | 先新表分区，旧表不原地改造 |
| 状态更新频率过高 | Redis TTL、字段变更检测、更新节流 |

## 12. 推荐启动顺序

实际执行建议从以下任务开始：

```text
1. 梳理指标字典和事件类型
2. 编写新表迁移脚本
3. 实现 iot_metric_samples 双写
4. 实现 iot_device_latest_metrics 双写
5. 指标详情接口增加新表查询灰度开关
6. 做新旧查询结果对账
7. 引入批量落库和连接池
8. 报告页切最新指标表
9. 心跳拆表并接入 Redis TTL
10. 分区和汇总表落地
```

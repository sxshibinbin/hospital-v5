# IoT 性能测评报告（改造后复评）

日期：2026-07-29

## 1. 测评范围

本次复评基于当前已落地的第一阶段改造，重点评估以下链路：

- 设备事件上报接口：`POST /api/iot/subscribe`
- 上报文件落盘、文件监听和后台落库
- 健康指标详情接口：`POST /api/iot/device/metric/trend`
- 设备检测报告接口：`POST /api/iot/device/report`
- 单设备报警接口：`POST /api/iot/devices/alarm`
- 设备信息接口：`POST /api/iot/device/get`
- 新拆分表在千万级、亿级增长下的扩展风险

说明：本报告是基于代码实现、数据库结构、样本数据和 SQL 执行计划的静态复评，不等同于完整压测报告。最终上线容量仍需要用真实上报样本压测确认。

## 2. 核心结论

当前第一阶段改造后，系统相比旧报告中的状态已经有明显改善：

1. `/api/iot/subscribe` 已增加绑定设备过滤，未绑定设备不再写文件，减少无效文件 IO 和后续落库压力。
2. IoT 数据库连接已改为连接池，避免每条事件新建数据库连接。
3. 文件监听已改为按批读取、按批 checkpoint，checkpoint 写放大明显降低。
4. 事件表已拆为健康、报警、心跳三类新表；旧表仅作为验证期对账依据，验证完成后移除旧表写入。
5. 健康指标属性表 `iot_health_event_items.attr_value` 已为 `DOUBLE PRECISION`，指标趋势查询不再做文本正则转换。
6. 设备报告页最新指标已切到 `iot_device_latest_metrics`，并通过 `(imei, attr_name)` 唯一索引保证并发安全。
7. 报警接口已切到 `iot_alarm_events`，避免继续扫描旧事件总表。

按 4000 台设备、每 5 分钟 1 条数据估算，平均事件量约 13.33 条/秒。当前实现支撑这个平均负载的可行性比改造前高很多，尤其是查询侧已经消除了最主要的文本数值转换瓶颈。

但当前版本仍不能直接判断为生产容量充分，主要原因是：

1. 文件监听批内事件表、属性表和最新指标表已改为多行批量写入，但设备绑定缓存、设备基础信息比对仍按事件逐条处理。
2. 设备报告页按用户查询，当前业务约束为单用户最多 5 台设备；最新上报时间/状态仍从三张事件表查询，但已调整为每张表内部先取最新 1 条，当前不属于主要瓶颈。
3. 分区本次未做，千万级后短期能跑，但亿级后表维护、索引膨胀、归档和 vacuum 风险仍在。
4. IoT 设备快照缓存当前是进程内存对象，不是 Redis；单进程可用，多进程/多实例时缓存不会共享。

总体判断：第一阶段改造后，可以进入小规模真实数据观察和针对性压测；若要稳定承载 4000 台设备长期生产运行，建议至少再完成“监控指标补齐、真实压测”。分区可以按当前决策放到二期，但需要在数据进入亿级前完成。

## 5. 当前实现评估

### 5.1 上报接收接口

位置：`backend/iot_subscription/router.py`

当前 `/api/iot/subscribe` 逻辑：

1. 解析请求 JSON。
2. 获取 `imei`。
3. 调用 `is_bound_device_for_ingest()` 判断是否为已绑定设备。
4. 未绑定或未知设备直接返回 `success`，不写文件。
5. 已绑定设备写入本地 RAW 文件，后续由文件监听落库。

优势：

1. 接口主路径仍然不直接落库，避免平台回调被数据库慢写拖住。
2. 未绑定设备过滤前置，能减少无效文件写入和无效落库。
3. 已绑定设备命中进程内缓存后，过滤判断成本很低。

风险：

1. 首次命中某个 IMEI 或缓存过期时，会查询数据库；上报端如果集中出现大量新 IMEI，会增加数据库回源压力。
2. 当前缓存是进程内对象，不是 Redis。单进程部署没问题，多进程或多实例部署时缓存不共享。
3. 接口仍会记录完整 payload 日志，突发上报时日志 IO 可能成为额外压力。

评估：

平均 13.33 events/s 下，上报接收层风险较低。需要关注的是突发场景下“缓存未命中 + 日志写入 + 文件写入”的组合压力。

### 5.2 文件监听和落库

位置：`backend/iot_subscription/file_monitor.py`

当前文件监听逻辑：

1. 每轮扫描待处理文件。
2. 从 `iot_file_offsets` 读取 offset。
3. 按 `IOT_FILE_BATCH_SIZE=200` 或 `IOT_FILE_BATCH_SECONDS=20` 读取一批数据。
4. 每批使用一个数据库连接。
5. 批内调用 `process_events_batch()`，事件表、属性表和最新指标表使用多行 `INSERT/UPSERT`。
6. 每批完成后更新一次 checkpoint。

已经解决的问题：

1. 不再每条数据更新 checkpoint。理想 200 条一批时，1,152,000 条/天只需约 5,760 次 checkpoint；即使实时低水位场景按 2 秒轮询写 checkpoint，也约 43,200 次/天，仍明显低于逐条 checkpoint。
2. 每批使用一个连接，连接创建成本明显下降。
3. 失败时 checkpoint 回退到批起点，具备重试能力。

仍存在的问题：

1. 文件监听是单消费者模型，不能自动利用连接池最大 10 个连接并行追 backlog。
2. `IOT_FILE_BATCH_SECONDS=20` 当前更像“单次处理最长时间限制”，不是严格的“攒 20 秒再批量提交”。在实时流量较低时，每批大小大概率接近 2 秒内新增数据，约 26 条，而不是 200 条。
3. 设备快照加载、设备基础信息变化判断仍然按事件逐条进行；缓存命中时成本较低，缓存未命中或基础信息频繁变化时仍会增加 SQL。

评估：

当前落库链路比旧版本安全很多，事件、属性和最新指标写入已经完成真正的批量化。平均流量预计可跑，5 倍和 10 倍突发仍需要压测确认。若单消费者落库速度低于平台上报速度，backlog 仍会增长。

### 5.3 单批事件写入评估

位置：`backend/iot_subscription/database.py`

当前 `process_event()` 写入顺序：

1. 绑定设备缓存/数据库回源。
2. 设备基础信息有变化才更新。
3. 新分类事件表写入：`iot_health_events` / `iot_alarm_events` / `iot_heartbeat_events`。
4. 新分类属性表写入。
5. 健康指标写入 `iot_device_latest_metrics`。

说明：当前验证期代码仍保留旧表写入用于对账，验证完成后会移除；本节按正式运行的“新表主写入”评估。

在缓存命中且设备基础信息无变化时，批量后数据库往返次数主要由“涉及哪些表”决定，不再随属性条数线性增加。粗略估算如下：

| 场景 | 单批 SQL 往返估算 |
|---|---:|
| 仅心跳事件 | 约 2 次/批：心跳事件、心跳属性 |
| 仅健康事件 | 约 3 次/批：健康事件、健康属性、最新指标 |
| 仅报警事件 | 约 2 次/批：报警事件、报警属性 |
| 健康和报警混合 | 约 5 次/批：健康事件、健康属性、报警事件、报警属性、最新指标 |

多行批量写入后，网络往返和解析成本下降明显；数据库实际写入的行数仍取决于事件数、属性数、事件分类和索引数量。当前本地小样本不能证明生产峰值能力。

关键判断：

当前写入侧的主要不确定性不再是 SQL 往返次数，而是批量写入在真实突发流量下的事务耗时、索引维护、磁盘 IO 和单消费者追 backlog 能力，需要通过压测确认。

### 5.4 设备基础信息和联系人更新

当前通过缓存快照比较 `deviceState`、`site`、联系人等字段，有变化才更新 `iot_devices` 和 `iot_device_contacts`。

优势：

1. 避免每次上报都无差别更新设备基础信息表。
2. 减少 `iot_devices` 和 `iot_device_contacts` 的 dead tuple、锁竞争和索引维护。
3. 对 4000 台设备这种低频状态变更场景是合理的。

风险：

1. 进程重启后缓存为空，首轮每台设备会回源数据库。
2. 多进程部署时每个进程各自回源，缓存收益降低。
3. 如果后续在外部修改设备基础信息，需要确保删除或刷新对应 IMEI 缓存。

评估：

单进程部署下，该优化可以有效降低基础信息表写放大。多实例部署时建议切到 Redis 或增加统一缓存失效机制。

## 6. 查询侧评估

### 6.1 指标详情接口

接口：`POST /api/iot/device/metric/trend`

当前数据源：`iot_health_event_items`

已经解决的问题：

1. 不再查询旧大表 `iot_event_items`。
2. `attr_value` 已是 `DOUBLE PRECISION`，不再做 SQL 正则和类型转换。
3. 当前 SQL 可使用 `idx_iot_health_items_imei_attr_sign_id`。

实测执行计划显示，单设备、单指标、时间范围查询可以命中：

```text
Bitmap Index Scan on idx_iot_health_items_imei_attr_sign_id
```

在 4000 台设备、5 分钟一条数据下，单设备单指标的数据量估算：

| 查询范围 | 单指标行数估算 |
|---|---:|
| 1 天 | 288 |
| 7 天 | 2,016 |
| 30 天 | 8,640 |
| 1 年 | 105,120 |

评估：

指标详情接口从“全表大数据风险”变成了“按设备、指标、时间范围的索引扫描风险”。这是一项实质性改善。即使 `iot_health_event_items` 表整体达到千万级，只要查询始终带 `imei + attr_name + sign_time`，短周期和中周期查询应可接受。

剩余风险：

1. 年级别查询仍会扫描单设备单指标约 10 万行，多个指标会叠加。
2. 跨设备统计不能直接扫原始明细表，需要汇总表。
3. 表不分区时，亿级后索引维护、vacuum、归档和备份压力仍会上升。

建议：

1. 日/周/月详情继续查 `iot_health_event_items`。
2. 年视图或跨设备统计优先建设小时/天汇总表。
3. 二期做时间分区，优先对 `iot_health_event_items` 和 `iot_heartbeat_events` 分区。

### 6.2 设备检测报告接口

接口：`POST /api/iot/device/report`

当前数据源：

| 数据 | 当前来源 |
|---|---|
| 用户绑定设备 | `iot_user_devices` + `iot_devices` |
| 最新指标 | `iot_device_latest_metrics` |
| 雷达今日报警数 | `iot_alarm_events` |
| 最新上报时间/状态 | `iot_alarm_events` / `iot_health_events` / `iot_heartbeat_events` |

已经解决的问题：

1. 手环/手表指标不再从 `iot_event_items` 做 `DISTINCT ON`。
2. 最新指标表最大规模约为 `设备数 * 指标数`，4000 台设备、6 个核心指标约 24,000 行，读取成本很低。
3. `iot_device_latest_metrics(imei, attr_name)` 唯一索引已建立，写入并发安全。
4. 今日报警数已改查 `iot_alarm_events`，报警稀疏时查询压力较低。

剩余风险：

当前最新上报时间/状态使用三张事件表 `UNION ALL`，并且按每台设备做 lateral 查询。由于设备报告页按用户查询，且当前业务约束为单用户最多 5 台设备，因此每次报告页最多约 15 次索引探测，当前不构成主要性能瓶颈。

该查询已完成小优化：每张事件表内部先按 `sign_time DESC, id DESC` 取最新 1 条，再对最多 3 条候选记录做最终排序，避免单设备历史事件变大后拉取多条历史记录参与排序。

建议：

1. 保留当前三张事件表查询，不新增最新事件状态表。
2. 继续依赖每张事件表的 `(imei, sign_time DESC, id DESC)` 索引。
3. 只有当后续出现按机构、楼层、科室批量查看几百到几千台设备的页面时，再评估新增 `iot_device_latest_events` 或类似最新状态表。

评估：

当前报告页对 4 台设备 smoke test 返回正常；在单用户最多 5 台设备的业务约束下，报告页最新事件查询风险降为观察项。

### 6.3 单设备报警接口

接口：`POST /api/iot/devices/alarm`

当前数据源：`iot_alarm_events`

优势：

1. 报警数据已经从总事件表拆出，日常数据量远小于健康和心跳。
2. 已有 `idx_iot_alarm_events_imei_sign_time`，单设备按时间范围查报警具备索引基础。
3. `handler_status / handle_time / alarm_reason` 已在报警表中，后续报警处置功能可以直接落在新表。

剩余风险：

如果频繁按 `deviceImei + handlerStatus + 日期范围` 查询，当前更匹配的索引应为：

```sql
CREATE INDEX idx_iot_alarm_events_imei_handler_time
ON iot_alarm_events (imei, handler_status, sign_time DESC, id DESC);
```

当前已有 `handler_status + sign_time` 和 `imei + sign_time` 两类索引，数据量小时没有问题；报警量大后，组合过滤可以再补这个索引。

### 6.4 设备信息接口

接口：`POST /api/iot/device/get`

当前逻辑：

1. 基础状态优先读 `iot_devices.device_state`。
2. 最新上报时间从三张事件表取最新记录。

评估：

单设备查询压力较低。最新事件 union 查询已按每张事件表内部最新 1 条优化，当前风险较低。

## 7. 表拆分和容量评估

### 7.1 健康事件和健康属性

健康指标查询已经明显受益于拆表和数值化。`iot_health_event_items` 会是后续增长最快、查询最频繁的明细表。

建议容量边界：

| 阶段 | 行数规模 | 建议动作 |
|---|---:|---|
| 1000 万以内 | 可继续观察 | 保持索引、慢 SQL 和表大小监控 |
| 1000 万到 1 亿 | 建议开始二期 | 做时间分区和汇总表 |
| 1 亿以上 | 必须治理 | 分区、归档、汇总、冷热分层 |

### 7.2 报警事件和报警属性

报警事件理论上稀疏，拆表后压力最小。该表更关注业务功能扩展，例如处理状态、处理时间、报警原因。

风险主要不是写入量，而是查询组合索引是否匹配报警列表、待处理报警、机构统计等后续功能。

### 7.3 心跳事件和心跳属性

心跳数据日常查询频率低，但数据量可能很大。拆出心跳表是正确方向。

建议：

1. 心跳表优先做归档或保留周期策略。
2. 设备在线判断尽量不扫心跳历史，可读最新状态或最新事件表。
3. 二期分区时，`iot_heartbeat_events` 应是优先对象之一。

## 9. 当前版本风险排序

| 优先级 | 风险 | 影响 | 建议 |
|---|---|---|---|
| P0 | 缺少真实性能压测 | 无法确认 5 倍、10 倍突发能力 | 立即做 15/75/150 events/s 三档压测 |
| P1 | 没有落库监控和 backlog 告警 | 问题发现滞后 | 补 events/s、items/s、backlog、落库延迟 |
| P1 | `iot_device_latest_metrics` 高频 upsert | 小表高更新产生 dead tuple | 观察 autovacuum，必要时调 fillfactor/autovacuum |
| P2 | 报告页最新事件查询按设备扫三张表 | 单用户最多 5 台设备，当前影响较低 | 保持观察；出现机构级批量设备页时再评估最新事件表 |
| P2 | 未分区 | 亿级后维护和归档困难 | 二期做时间分区 |
| P2 | 进程内缓存 | 多实例缓存不一致 | 多实例前改 Redis 或统一缓存层 |

## 10. 压测建议

### 10.1 写入压测

| 档位 | 事件速率 | 持续时间 | 目标 |
|---|---:|---:|---|
| 基准 | 15 events/s | 30 分钟 | 覆盖目标平均流量 |
| 峰值 | 75 events/s | 20 分钟 | 覆盖 5 倍突发 |
| 极限 | 150 events/s | 10 分钟 | 覆盖 10 倍突发和补报 |

压测数据要求：

1. 覆盖 4000 个不同 IMEI。
2. 健康、心跳、报警按真实比例混合。
3. 健康事件至少覆盖心率、血氧、舒张压、收缩压、温度、计步。
4. 包含重复 signature，验证幂等。
5. 包含未绑定 IMEI，验证前置过滤效果。

写入验收建议：

| 指标 | 建议目标 |
|---|---:|
| `/api/iot/subscribe` p95 | 小于 100 ms |
| `/api/iot/subscribe` p99 | 小于 300 ms |
| 平均流量落库延迟 | 小于 30 秒 |
| 5 倍突发后 backlog 追平 | 20 分钟内 |
| 文件 checkpoint backlog | 持续可下降 |
| 数据库连接池耗尽 | 不应出现 |
| 重复 signature | 不产生重复事件 |

### 10.2 查询压测

| 接口 | 数据规模 | 建议目标 |
|---|---|---:|
| 指标详情 1 天 | 单设备单指标 | p95 小于 300 ms |
| 指标详情 7 天 | 单设备单指标 | p95 小于 500 ms |
| 指标详情 30 天 | 单设备单指标 | p95 小于 800 ms |
| 指标详情 1 年 | 单设备单指标 | p95 小于 1500 ms，建议走汇总 |
| 设备报告 | 单用户最多 5 台设备 | p95 小于 300 ms |
| 单设备报警 | 30 天 | p95 小于 500 ms |

查询压测需要预置至少 1000 万行 `iot_health_event_items`，否则无法验证千万级索引和聚合表现。

## 11. 下一步建议

### 11.1 立即做

1. 对当前版本进行三档写入压测。
2. 对 `iot_health_event_items` 预置千万级数据后压测指标详情。
3. 增加落库监控：待处理文件数、待处理字节、events/s、items/s、落库延迟、错误批次数。
4. 观察 `iot_device_latest_metrics` dead tuple 和 autovacuum。

### 11.2 第一阶段稳定后做

1. 补充报警接口组合索引：`imei + handler_status + sign_time`。

### 11.3 二期做

1. 健康属性表、心跳事件表按时间分区。
2. 建小时/天汇总表，服务年视图和跨设备统计。
3. 心跳历史归档和保留周期。
4. 多实例部署前，将 IoT 设备快照缓存切到 Redis。

## 12. 最终判断

本次第一阶段改造已经解决了旧报告中最核心的查询瓶颈：指标数值存文本、查询时正则转换、报告页从明细表取最新值。这使得指标详情和报告页在千万级数据前具备了更好的可扩展性。

写入链路也已经从“逐条建连、逐条 SQL、逐条 checkpoint”改善为“连接池、批量事件/属性写入、批后 checkpoint”。当前剩余的主要不确定性是缺少真实压测和运行监控。

因此当前结论是：

1. 平均 4000 台设备、5 分钟一条的目标流量，当前版本有较大概率可以支撑。
2. 5 倍、10 倍突发以及长时间 backlog 追赶能力，必须通过压测验证。
3. 查询侧短期风险已从 P0 降到 P1/P2；写入侧仍有 P0 风险。
4. 真正进入长期生产前，应至少完成压测和监控补齐。

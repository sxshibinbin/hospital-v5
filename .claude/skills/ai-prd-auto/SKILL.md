# 需求分析技能

将用户的自然语言需求转化为结构化需求文档、可交互原型、开发任务列表，支持TFS工作项创建。

## 执行模式

本技能支持三种执行模式：

| 模式 | 触发条件 | 执行流程 | 产物目录 | 特点 |
|------|----------|----------|----------|------|
| **临时模式** | 无 `tfs_work_item_id` | 单路径(A) | `DOCS/.temp/{uuid}/` | 快速分析，等待主Skill确认 |
| **组织模式** | 有 `tfs_work_item_id` | 单路径(A) | `DOCS/{需求号}/` | 直接TFS集成，完整流程 |
| **A/B双路径模式** | 判定触发+用户确认 | 双路径并行 | `DOCS/{需求号}/AB/` | 高可靠性，综合评判择优 |

**模式判定逻辑**（按优先级）：
1. **A/B模式优先判定**（步骤0.5）：无论有无 `tfs_work_item_id`，先执行A/B模式必要性判定
2. 有 `tfs_work_item_id` + 无 `temp_output_dir` → **组织模式**
3. 有 `tfs_work_item_id` + 有 `temp_output_dir` → **组织模式（迁移）**
4. 无 `tfs_work_item_id` → **临时模式**

> 变量约定：文档中 `{output_dir}` 在组织模式下为 `DOCS/{需求号}/`，临时模式下为 `DOCS/.temp/{uuid}/`，A/B模式下为 `DOCS/{需求号}/AB/`。

## 关键确认机制（v1.19.0 强化）

**核心原则**：临时模式询问、需求设计和原型设计阶段完成后，必须经过人工确认才能进行下一步。

**⚠️ v1.19.0 特别强调**：步骤A3.5是临时模式的关键转折点，**不得跳过**。若跳过A3.5直接执行A4，用户将失去创建TFS需求号的机会，导致后续Git推送和TFS下发无法执行。

### 确认环节位置

| 确认环节 | 触发时机 | 确认内容 | 阻塞后续步骤 | 执行条件 |
|----------|----------|----------|--------------|----------|
| **步骤A3.5** ⭐v1.19.0强化 | 需求分析完成后（A3结束后） | 是否创建TFS需求号并转组织模式 | 步骤A4（PRD生成） | **仅临时模式**（无tfs_work_item_id）**必须执行** |
| **步骤A4.2** | PRD文档生成后 | PRD内容是否符合需求 | 步骤A5（原型设计） | 所有模式 |
| **步骤A5.2** | 原型生成后 | 原型设计是否符合需求 | 步骤A6（核验）、步骤A7（任务拆分） | 所有模式 |

**⚠️ A3.5执行判断表**（v1.19.0 新增）：
| 模式判断 | tfs_work_item_id | 下一步动作 |
|----------|------------------|------------|
| **临时模式** | 无（用户直接输入需求） | **必须执行A3.5**询问创建需求号，**禁止跳过** |
| **组织模式** | 有（用户提供需求号） | **跳过A3.5**，直接执行A4 |
| **A/B模式** | 有或无 | **跳过A3.5**（A/B模式有单独的整合后询问流程） |

### 确认机制

每个确认环节使用 `AskUserQuestion` 工具，必须包含以下选项：

```
AskUserQuestion({
  questions: [
    {
      header: "{阶段名称}确认",
      question: "{阶段产物名称}已生成完成，请确认是否符合需求？",
      multiSelect: false,
      options: [
        {
          label: "确认，继续下一步",
          description: "产物符合需求，继续执行后续流程"
        },
        {
          label: "需要调整",
          description: "产物需要修改，请说明具体调整内容"
        },
        {
          label: "重新生成",
          description: "产物不符合需求，重新生成"
        }
      ]
    }
  ]
})
```

### 确认结果处理

| 用户选择 | 处理动作 |
|----------|----------|
| **"确认，继续下一步"** | 解除阻塞，继续执行后续步骤 |
| **"需要调整"** | 根据用户反馈调整产物，调整后再次请求确认 |
| **"重新生成"** | 重新执行当前步骤，重新生成产物 |

**阻塞逻辑**：
- 用户未确认前，不得执行后续步骤
- 确认环节没有"跳过"选项，强制人工确认
- 若用户选择"需要调整"或"重新生成"，需完成调整/重新生成后再次确认

## A/B 双路径模式（v1.8.0 新增）

### 概述

A/B双路径模式是一种高可靠性需求分析方法，通过并行执行两种不同的分析路径，综合评判后择优整合，提高需求分析的准确性和完整性。

**核心价值**：
- **双重验证**：两种独立分析方法交叉验证，降低遗漏风险
- **视角互补**：传统PRD分析聚焦功能实现，OpenSpec探索聚焦问题空间和架构决策
- **择优整合**：综合评判选择最优方案，补充缺失部分

**代价**：
- 耗时约2-3倍（双路径并行 + 综合评判）
- Token消耗增加约2倍
- 需要用户确认启动

### 启动时机判断

A/B模式的启动时机由模型智能判定，遵循以下标准：

#### 判定维度（满分100分）

| 维度 | 权重 | 判定标准 | 分值 |
|------|------|----------|------|
| **复杂度** | 40% | 涉及系统模块数≥3、业务流程≥5步、数据库表≥5个 | 0-40分 |
| **风险等级** | 30% | 涉及核心业务、数据安全、用户权限、性能瓶颈 | 0-30分 |
| **新颖度** | 20% | 项目首次开发类似功能、无历史代码参考 | 0-20分 |
| **争议性** | 10% | 用户描述存在歧义、需求边界模糊、技术方案不确定 | 0-10分 |

**判定规则**：
- **总分 ≥ 60分**：建议启动A/B模式，必须询问用户确认
- **总分 40-59分**：可选启动，询问用户意愿
- **总分 < 40分**：不建议启动，执行单路径模式

#### 特殊触发条件（无需计算，直接触发）

以下情况直接建议启动A/B模式：

| 触发条件 | 触发时机 | 说明 |
|----------|----------|------|
| **用户明确指定** | 输入解析阶段 | 用户消息包含"A/B模式"、"双路径"、"综合分析"等关键词 |
| **分析中途触发** | 步骤1-3执行中 | 发现需求模糊、架构冲突、技术方案争议 |
| **关键业务场景** | 步骤0判定 | 涉及患者安全、财务结算、权限管理等高风险场景 |

## 输入解析

从用户消息中提取以下信息：
- `raw_input`：用户的原始需求描述文本（可来自 TFS 工作项内容、手动输入）
- `context`：可选上下文字典，可包含：
  - `clarification_answers`：前一轮澄清的答案列表
  - `project_tech`：原型技术栈偏好，`"vue"` 或 `"html"`
  - `existing_repo_path`：现有代码仓库路径
  - `tfs_work_item_id`：TFS需求ID（有则触发组织模式）
  - `temp_output_dir`：临时产物目录路径（仅迁移桥接场景）
  - `force_ab_mode`：强制启动A/B模式（用户明确指定）

若用户消息中包含JSON格式的上下文，直接解析使用；否则从自然语言中推断。

## 执行流程

### 步骤0：需求可行性验证（必执行）

**目的**：在投入资源生成 PRD 之前，验证需求是否已实现或是否需要完整开发流程。避免对已完成需求、纯配置变更、已有代码覆盖的需求重复生成 PRD。

**两种模式均执行**，区别在于 TFS 查询仅组织模式可用：

| 子步骤 | 组织模式 | 临时模式 |
|--------|----------|----------|
| 0.1 TFS 状态查询 | ✅ 执行 | ⛔ 跳过 |
| 0.2 代码库查重 | ✅ 执行 | ✅ 执行 |
| 0.3 判定与分流 | ✅ 综合判定（TFS+代码） | ✅ 简化判定（仅代码） |

#### 0.1 查询 TFS 工作项状态（仅组织模式）

**使用明确的命令行调用**，而非模糊的自然语言指令：

```bash
# 查询工作项详情
node tools/tfs-query.mjs get <tfs_work_item_id>

# 查询工作项的子工作项关系
node tools/get-workitem-relations.mjs <tfs_work_item_id> children
```

**执行流程**：
1. 使用 `tfs-query.mjs get` 获取父需求详情
2. 使用 `get-workitem-relations.mjs` 获取子工作项列表
3. 提取关键信息：父需求状态、子任务状态分布、子任务类型分布

提取以下关键信息：
- 父需求状态（新建议/活动/已分析/已解决/已关闭/已移除）
- 子任务状态分布（有多少已完成、多少进行中）
- 子任务类型分布（分析任务、开发任务、测试任务）

**标记自动化开发启动**：若父需求状态为"已建议"或"活动"（新需求，非已完成/已废弃），立即给父需求打标签 `AI-AUTO-DEV`：

```bash
# 添加标签（使用明确的命令行调用）
node tools/tfs-query.mjs add-tags <tfs_work_item_id> AI-AUTO-DEV
```

**标签添加成功验证**：执行后检查返回的工作项信息中 `System.Tags` 字段是否包含 `AI-AUTO-DEV`。

#### 0.2 代码库现状检查（两种模式均执行）

**关键词提取**：组织模式下从 TFS 工作项标题和描述提取；临时模式下从 `raw_input` 中提取。提取内容包括功能模块名、关键字段名、核心实体名、SQL 表名/列名。

**检查分两层**：第一层查 TFS 关联提交（最可靠），第二层查本地代码（兜底）。

##### 0.2a TFS 关联提交查询（组织模式优先，临时模式跳过）

通过 TFS 工作项的 **ArtifactLink** 反向查找关联的 Git Commit（而非依赖 `git log --grep`，后者只能搜 commit message 且仅限于本地已有提交）：

1. **查询父需求 + 子任务的关联提交**：
   ```
   # 查询父需求
   node tools/get-workitem-commits.mjs <tfs_work_item_id> <项目名>
   # 查询每个子任务（从步骤0.1获取的子任务列表）
   node tools/get-workitem-commits.mjs <子任务ID> <项目名>
   ```
   注意：开发提交通常挂在"开发任务"子工作项上而非父需求，**必须同时查询子任务**。

2. **若 TFS API 返回了本地不存在的 commit**，尝试 fetch：
   ```
   git fetch origin <commit_hash>
   ```

3. **汇总所有提交的变更文件列表**，作为"已变更文件清单"供后续判定使用。

**降级**：若 `ai-tfs-integration` 或 `get-workitem-commits.mjs` 不可用，降级到 0.2b 本地搜索。

##### 0.2b 本地代码搜索（两种模式均执行）

1. **本地 Git 提交搜索**：搜索引用该需求号或核心关键词的提交
   ```
   git log --all --oneline --grep="<work_item_id 或 核心关键词>"
   ```

2. **关键词代码搜索**：用 Grep 在业务模块代码中搜索核心关键词（实体字段名、DTO 属性名、模块名），确认是否有已有实现
   - 后端实体/DTO/DAO 层
   - SQL mapper XML
   - 前端 Vue 组件

3. **关联需求追溯**：搜索 git log 中引用相同关键词的最近提交，识别是否有其他需求号已实现类似功能
   ```
   git log --all --oneline --grep="<核心关键词>" -- <相关文件路径>
   ```

##### 0.2c 综合结论

将 0.2a（TFS 关联提交）和 0.2b（本地代码搜索）的结果合并：
- **代码现状判断标准**：以 TFS 关联提交的变更文件为准（如果有）；以本地 Grep 搜索结果为补充
- **"有完整代码"** = TFS 关联提交中 80% 以上的变更文件在本地代码中已存在，且 Grep 搜索确认核心关键词已实现
- **"有部分代码"** = 核心关键词部分命中，但不是全部
- **"无代码"** = TFS 无关联提交 + 本地 Grep 无匹配 + git log 无匹配

#### 0.3 判定与分流

**组织模式判定矩阵**（结合 TFS 状态 + 代码检查）：

| TFS 状态 | 代码现状 | 判定结果 | 后续动作 |
|----------|----------|----------|----------|
| 已建议/活动 | 无代码 | **新需求** | 继续步骤0.5 |
| 已建议/活动 | 有部分代码 | **部分实现** | 标记已实现部分（文件路径+行号），继续步骤0.5，步骤3 中引用已有代码 |
| 已分析 | 无代码 | **待开发** | 继续步骤0.5 |
| 已解决/已关闭 | 有完整代码 | **已完成** | **中止**，输出"需求已实现"报告，提示可能是配置问题 |
| 已解决/已关闭 | 无代码 | **状态不一致** | **中止**，警告：TFS 显示已解决但未找到关联提交。可能原因：①提交挂在子任务上（检查子任务 ArtifactLink）②提交在其他仓库 ③状态不准确 |
| 已移除 | — | **已废弃** | **中止**，输出废弃信息 |
| 任意 | 有其他需求号实现 | **重复需求** | 报告关联需求号，询问用户是否仍需生成 PRD |

**临时模式判定矩阵**（仅代码检查）：

| 代码现状 | 判定结果 | 后续动作 |
|----------|----------|----------|
| 无匹配 | **新需求** | 继续步骤0.5 |
| 有部分匹配 | **疑似重复** | 展示匹配到的代码文件列表和关联需求号，通过 `AskUserQuestion` 询问用户"是否继续生成 PRD？" |
| 精准匹配（字段名、表名、模块名全命中） | **强烈疑似重复** | 展示匹配详情，警告用户该功能可能已实现，由用户决定继续或中止 |

**临时模式询问格式**：
```
AskUserQuestion:
  问题: "代码库中发现疑似已有实现，是否继续生成 PRD？"
  选项:
    - "继续生成 PRD" — 忽略匹配结果，正常执行
    - "中止" — 停止执行，输出匹配结果
```

#### 0.4 中止输出格式

不生成 PRD 时，输出以下格式：
```
状态: skip
原因: {判定结果说明}
需求状态: {TFS状态 或 "手动输入"}
代码现状: {已有代码文件列表 或 "无"}
关联需求: {关联需求号列表 或 "无"}
建议: {下一步建议}
```

#### 0.5 降级策略

- **组织模式 TFS 查询失败** → 记录 WARN 日志 → 降级为临时模式判定逻辑（仅 0.2b 本地搜索）
- **组织模式 TFS 子任务查询失败** → 仅查父需求关联提交，记录 WARN
- **`get-workitem-commits.mjs` 返回了本地不存在的 commit** → 尝试 `git fetch origin <hash>` 拉取；fetch 失败时标注"远端提交未同步"
- **两种模式 git 搜索失败**（如非 git 仓库） → 记录 WARN → 跳过 git 搜索，仅执行 Grep 代码搜索
- **两种模式 Grep 也失败** → 记录 WARN → 继续步骤0.5（保守放行）
- **原则：宁可放行不可阻塞。有疑问时让用户决策，不自主中止。**

   - 检查 `raw_input` 是否包含高风险关键词：`患者安全`、`财务结算`、`权限管理`、`数据迁移`、`核心业务`、`性能瓶颈`
   - 命中 → **建议启动，进入确认环节**

#### 0.5.2 复杂度评分计算（无特殊触发时执行）

**评分维度**：

| 维度 | 评估方法 | 分值范围 |
|------|----------|----------|
| **复杂度(40%)** | 识别系统模块数、业务流程步骤数、数据库表数 | 0-40分 |
| **风险等级(30%)** | 检查是否涉及安全、权限、性能、核心业务 | 0-30分 |
| **新颖度(20%)** | 检查项目是否有类似功能历史代码 | 0-20分 |
| **争议性(10%)** | 检查需求描述是否存在歧义词汇 | 0-10分 |

**评分细则**：

**复杂度评分**：
- 模块数≥5 或 流程≥8步 或 表数≥8个 → 40分（满分）
- 模块数3-4 或 流程5-7步 或 表数5-7个 → 25分
- 模块数≤2 或 流程≤4步 或 表数≤4个 → 10分

**风险等级评分**：
- 涉及患者安全/财务结算/权限管理 → 30分（满分）
- 涉及数据安全/用户隐私 → 20分
- 涉及性能优化/用户体验 → 10分
- 无明显风险 → 5分

**新颖度评分**：
- Grep搜索无匹配，项目首次开发 → 20分（满分）
- 有部分匹配，需大幅扩展 → 10分
- 有完整参考代码 → 0分

**争议性评分**：
- 需求描述存在明确歧义（如"支持多种方式"未具体） → 10分（满分）
- 需求边界模糊 → 5分
- 需求清晰明确 → 0分

**计算示例**：
```
总分 = 复杂度分值 + 风险分值 + 新颖度分值 + 争议性分值
例：复杂度25分 + 风险20分 + 新颖度20分 + 争议性5分 = 70分
```

#### 0.5.3 判定结果与分流

| 总分范围 | 判定结果 | 后续动作 |

### 步骤0.7：功能调整影响范围评估（v1.12.0 新增）

**目的**：当需求是对现有功能进行调整时，利用GitNexus代码知识图谱评估改造的影响范围，生成影响范围文档和测试范围文档，指导后续开发和测试。

**执行时机**：
- 步骤0.3判定为"部分实现"（有部分代码需扩展）
- 用户需求描述明确表示"修改"、"调整"、"优化"现有功能
- 原型确认时用户选择基于现有代码进行调整

**不执行时机**：
- 步骤0.3判定为"新需求"（无匹配代码）
- 步骤0.3判定为"已完成"（中止流程）

#### 0.7.1 功能调整类型识别

根据需求描述和代码检查结果，识别调整类型：

| 调整类型 | 特征 | 影响评估方式 |
|----------|------|--------------|
| **UI调整** | 页面布局、样式、交互变更 | 查找组件调用链，评估UI依赖 |
| **逻辑调整** | 业务流程、计算规则变更 | 查找函数调用链，评估逻辑依赖 |
| **数据调整** | 字段新增/删除/修改、API参数变更 | 查找数据流，评估数据依赖 |
| **性能优化** | 查询优化、缓存策略、响应时间改进 | 查找性能瓶颈点，评估优化影响 |
| **Bug修复** | 修复已知缺陷 | 查找Bug关联代码，评估修复影响 |

#### 0.7.2 GitNexus影响分析流程

**核心工具**：使用GitNexus MCP工具进行代码知识图谱分析

| 分析维度 | GitNexus工具 | 用途 |
|----------|--------------|------|
| **符号影响** | `gitnexus_impact` | 分析修改某个函数/类的blast radius |
| **调用链** | `gitnexus_context` | 获取符号的完整上下文（调用者/被调用者） |
| **执行流** | `gitnexus_query` | 查询相关执行流程 |
| **变更检测** | `gitnexus_detect_changes` | 检测未提交变更的影响 |
| **API影响** | `gitnexus_api_impact` | 分析API路由的影响范围 |

**分析步骤**：

1. **提取关键符号**：从需求描述和现有代码中提取需要修改的关键符号（函数名、类名、组件名、API路由）

2. **逐符号影响分析**：
   ```
   对每个关键符号执行：
   gitnexus_impact({
     target: "符号名",
     direction: "upstream",  // 查找调用者（谁依赖这个符号）
     maxDepth: 3,            // 查找3层依赖
     includeTests: true      // 包含测试文件
   })
   ```

3. **汇总影响范围**：
   - d=1：直接依赖者（WILL BREAK）
   - d=2：间接依赖者（LIKELY AFFECTED）
   - d=3：潜在影响者（MAY NEED TESTING）

4. **API路由影响**（若涉及API）：
   ```
   gitnexus_api_impact({
   ```

AI可以根据需求描述的完整性和清晰度，自主判断是否需要进行澄清。

**需要澄清的场景**（必须询问）：
- 用户描述模糊、存在歧义
- 功能边界不清晰
- 缺少关键信息（数据来源、权限、异常处理）
- 涉及多个角色/场景，需要细化
- 用户明确要求澄清

**可以跳过澄清的场景**（自主判断）：
- 需求描述完整、清晰、无歧义
- 功能边界明确
- 已有充分的上下文信息（如来自TFS工作项的详细描述）
- 用户明确表示"不需要澄清"或"直接生成"

若判断需要澄清，生成 **至少3个，最多5个** 关键澄清问题。使用 `AskUserQuestion` 询问。


**子任务创建流程（v1.26.0 强制流程）**：

```
# 步骤1：读取任务索引文件，获取任务总数
Read {output_dir}/任务拆分/任务索引.md

# 步骤2：记录日志 - 开始创建子任务

  node tools/tfs-query.mjs create-child-task <tfs_work_item_id> "{task.name}" "{task.description}" "" {task.hours}
  # 记录日志：[INFO] 步骤7.5.1-创建子任务：{task.name}子任务ID={返回的ID}
```

**详细流程说明**：

1. **读取任务列表**：读取 `{output_dir}/任务拆分/任务索引.md`，提取所有任务的名称和预估工时
2. **循环创建**：为每个任务（从任务1到任务N）逐个执行 `create-child-task` 命令
3. **状态默认值**：命令自动将子任务状态设为"活动"，预估工时写入初始估计字段
4. **项目信息获取**：命令自动获取父需求的项目信息并创建关联的子任务
5. **验证创建结果**：使用 `get-workitem-relations.mjs` 验证子任务数量与任务索引数量一致
6. **记录子任务ID**：将创建的所有子任务ID记录到 `execution_index.json` 的 `tasks` 数组

**⚠️ 需求分析子任务特殊处理**：
- 需求分析子任务名称固定为"需求分析-{需求标题}"或"需求分析"
- 预估工时参考传统人工分析时间，默认设置为**4小时**
- 创建后状态为"活动"，需求分析流程完成后需关闭（见步骤7.5.1.5）

**⚠️ v1.26.0 新增验证要求**：

```

# 验证日志

```

**常见错误处理**：
| 错误情况 | 处理方式 |
|----------|----------|
| 子任务数量少于任务索引 | 记录错误，重新创建缺失的子任务 |
| 创建命令执行失败 | 记录错误到tfs_errors，继续创建下一个 |
| 预估工时参数非数字 | 检查任务索引的hours字段格式 |

##### 7.5.1.5 关闭需求分析子任务（v1.27.0 强制完整状态流转）

**执行时机**：需求分析流程完成后（步骤A7任务拆分完成后），立即关闭"需求分析"子任务并添加标签。

**⚠️ v1.27.0 核心要求**：需求分析子任务必须完整流转到 `finalState`（已关闭），不能停留在 `resolvedState`（已解决）。必须执行两步状态流转：活动 → 已解决 → 已关闭。

**原因**：需求分析子任务是记录需求分析工作的任务项，当AI完成需求分析（生成PRD、原型、任务拆分）后，该任务已全部完成，应直接标记为最终关闭状态"已关闭"。完整状态流转：活动 → 已解决 → 已关闭。

**⚠️ 其他子任务保持活动状态**：除需求分析子任务外，其他子任务（如后端开发、前端开发等）应保持"活动"状态，不得修改。

##### 7.5.2 更新父需求状态（v1.28.0 顺序状态流转机制）

更新状态后必须验证实际状态是否为 `analysisCompleteState`：
- 若验证结果显示状态为"已分析" → 操作成功，继续步骤7.5.3
- 若验证结果显示状态为"活动" → **操作错误，状态未正确更新，记录ERROR日志**
- 若验证结果显示状态为其他值 → 记录WARN日志，说明实际状态

**错误处理（v1.26.0 新增）**：

| 错误情况 | 处理方式 |
|----------|----------|
| TFS不支持 `analysisCompleteState` 状态 | 记录WARN日志，保留当前状态，在最终输出中提示用户手动更新 |
| 状态更新命令执行失败 | 记录ERROR日志到tfs_errors，继续步骤7.5.3（打标签），不阻塞流程 |
| 验证状态不是 `analysisCompleteState` | 记录WARN日志，说明实际状态与预期不符，继续后续流程 |

> **v1.26.0 变更**：强制要求本步骤必须执行，使用 `analysisCompleteState` 配置值，新增状态验证步骤，若验证失败需记录错误日志。

##### 7.5.1.6 更新其他子任务状态为活动（v1.29.0 强化执行）

**⚠️ v1.29.0 核心强制要求**：创建子任务后，必须立即将所有非需求分析子任务的状态从创建时的初始状态（如"已建议"）更新为"活动"状态。此步骤是**强制步骤**，**绝对不得跳过**！

**⚠️ 为什么此步骤绝对不可跳过**：
1. 子任务创建时可能被TFS设置为"已建议"或"新建议"状态（非活动状态）
2. 开发任务（后端开发、前端开发等）需要处于"活动"状态才能被分配和执行
3. TFS状态流转规则要求：已建议 → 活动 → 已解决 → 已关闭
4. **若跳过此步骤，其他子任务将保持"已建议"状态，开发人员无法领取任务，后续开发流程将阻塞！**

**执行时机**：步骤7.5.1.5关闭需求分析子任务后**立即执行**，在步骤7.5.2之前执行。

**强制执行顺序验证**：
```
步骤7.5.1.5完成后 → 必须检查execution_index.json或progress.log → 确认7.5.1.6未执行 → ⭐强制执行7.5.1.6 → 验证所有子任务状态 → 执行步骤7.5.2
```

## ⚠️ Step 0.0: 前置分支检查（必须最先执行）

**核心目的**：确保当前工作区已提交，避免后续创建 worktree 和分支时出现冲突。

**⚠️ 为什么必须执行此步骤**：
- 当前工作区未提交时，创建新分支可能失败（分支名称冲突或工作区状态冲突）
- 创建 worktree 时可能失败（git worktree add 要求工作区干净）
- 后续 git push 步骤无法正常执行（新分支没有基准点）

### 执行步骤

1. **检查当前工作区状态**
   ```bash
   git status --porcelain
   ```

2. **判断结果**
   - 输出为空：工作区干净 → 进入 Step 0.1
   - 输出不为空：工作区有未提交的更改 → **必须询问用户处理方式**

3. **用户询问（使用 AskUserQuestion 工具）**

   当发现工作区有未提交的更改时：

   ```javascript
   AskUserQuestion({
     questions: [
       {
         header: "未提交更改",
         question: "当前工作区有未提交的更改，这将影响后续流程（创建分支和 worktree 可能失败）。请选择处理方式：",
         multiSelect: false,
         options: [
           {
             label: "自动提交（推荐）",
                         description: "调用 ai-git-push 技能自动提交当前更改，然后继续流程"
           },
           {
             label: "人工处理",
             description: "暂停流程，等待您手动处理未提交的更改后再继续"
           },
           {
             label: "取消流程",
             description: "终止本次自动化开发流程"
           }
         ]
       }
     ]
   })
   ```

### 用户选择处理方式

| 用户选择 | 处理方式 | 后续动作 |
|----------|----------|----------|
| 自动提交 | 调用 ai-git-push 子Agent | 提交成功后进入 Step 0.1 |
| 人工处理 | 输出提示，流程暂停 | 等待用户手动处理后重新触发技能 |
| 取消流程 | 输出取消信息 | 流程终止 |

```markdown

    subagent_type: "general-purpose",
    description: "提交当前工作区更改",
    prompt: `

你正在作为 ai-auto-dev 的子 Agent 执行前置提交任务。

### 任务信息
- 任务类型：前置提交（提交当前工作区更改）
- 目的：确保工作区干净后再创建 worktree

### ⚠️ 技能执行要求（强制遵守）

**你必须严格执行以下技能文件定义的流程：**

1. 首先使用 Read 工具读取技能文件：
   - 文件路径：.claude/skills/ai-git-push/SKILL.md

2. **严格按照技能文件中定义的步骤顺序执行**
3. **禁止跳过任何步骤**

### 完成后动作
1. 验证工作区状态（git status --porcelain 应为空）

`,
    model: "sonnet"
})
```

### 输出提示信息示例

**用户选择"人工处理"时**：

```

2. 确保工作区干净后（git status --porcelain 输出为空）
3. 重新触发 ai-auto-dev 技能继续流程

{列出 git status --porcelain 的输出内容}
```

**用户选择"取消流程"时**：

```
⚠️ 流程已取消

您取消了本次自动化开发流程。

当前工作区仍有未提交的更改，建议：
- 使用 ai-git-push 技能提交更改
- 或手动处理后再重新触发 ai-auto-dev 技能
```

### 完成后动作

- 工作区干净：立即进入 Step 0.1
- 用户选择自动提交且提交成功：进入 Step 0.1
- 用户选择人工处理：流程暂停，等待用户重新触发
- 用户选择取消流程：流程终止

## Step 7: 清理前验证

**核心目的**：验证前置步骤完成状态，确保流程完整性可追溯。

当流程中断或需要审计时，完整的日志记录能帮助定位问题节点。

### 执行步骤

1. **验证 Git 提交状态**
   - 使用 Read 工具读取 `worktree-{需求号}/DOCS/{需求号}/sched_log.md`
   - 检查 Step 6 状态是否为 success

2. **验证工作区状态**
   ```bash
   git -C worktree-{需求号} status --porcelain
   ```
   - 输出为空表示工作区干净

3. **更新 sched_log.md Step 7 部分**
   - 使用 Edit 工具替换 `<!-- STEP7_BLOCK -->` 到 `<!-- STEP7_END -->` 之间的内容

**验证通过时**：
```javascript

- **验证项**：-
- **验证结果**：-
- **执行时间**：-
- **备注**：-
<!-- STEP7_END -->`

new_string: `<!-- STEP7_BLOCK -->
### Step 7: 清理前验证
```

- 验证通过：进入 Step 8

## Step 8: 清理 Worktree

**核心目的**：释放开发隔离环境，完成资源回收。

保留未清理的 worktree 会占用磁盘空间并可能导致后续流程混淆。

### 执行步骤

1. **执行清理命令**
   ```bash
   git worktree remove worktree-{需求号} --force
   ```

2. **验证清理结果**
   ```bash
   git worktree list
   ```
   - 确认 worktree-{需求号} 不在列表中

3. **更新 sched_log.md Step 8 部分**
   - 使用 Edit 工具替换 `<!-- STEP8_BLOCK -->` 到 `<!-- STEP8_END -->` 之间的内容

### Edit 工具调用示例

**成功清理时**：
```javascript
old_string: `<!-- STEP8_BLOCK -->
### Step 8: 清理 Worktree
- **状态**：pending
- **清理操作**：-
- **清理结果**：-
- **执行时间**：-
- **备注**：-
<!-- STEP8_END -->`

new_string: `<!-- STEP8_BLOCK -->
### Step 8: 清理 Worktree
- **状态**：success
- **清理操作**：git worktree remove worktree-{需求号} --force
- **清理结果**：成功清理 - worktree 已移除
- **执行时间**：{当前时间}
- **备注**：清理完成，流程结束

```

**跳过清理时**（Step 7 失败）：
```javascript

### Step 8: 清理 Worktree
- **状态**：skipped
- **清理操作**：已跳过

- **执行时间**：-
- **备注**：需人工检查后手动清理
<!-- STEP8_END -->`
```

### 完成后动作

- 有其他需求号未处理：进入 Step 1 处理下一个
- 所有需求号已处理完毕：进入 Step 9

## Step 9: 更新调度日志最终状态

**核心目的**：汇总执行结果，提供流程完成度全景视图。

完整的汇总数据便于后续审计和统计分析。

### 执行步骤

1. **读取 sched_log.md 获取基础数据**
   - 获取启动时间（从文档头部）
   - 统计各步骤状态（success/failed/skipped）

2. **计算统计数据**
   - 完成时间：当前时间
   - 整体耗时：完成时间 - 启动时间
   - 成功步骤数：统计 success 状态的步骤数量
   - 失败/跳过步骤：列出对应步骤编号

3. **更新流程完成状态部分**
   - 使用 Edit 工具替换 `<!-- COMPLETION_BLOCK -->` 到 `<!-- COMPLETION_END -->` 之间的内容

## 注意事项

1. **工具调用顺序**：先 Read 读取文件，再 Edit 进行更新
2. **时间格式**：使用 `YYYY-MM-DD HH:MM:SS` 格式（如 `2026-05-27 14:30:00`）
3. **占位符完整性**：Edit 时保持 `<!-- ..._BLOCK -->` 和 `<!-- ..._END -->` 标记不丢失
4. **状态一致性**：更新后的状态值必须与实际执行结果一致

# Git Push Skill

将开发完成的代码提交并推送至远程仓库，推送成功后自动更新 TFS 子任务状态和需求状态（全自动执行，无需用户确认）。

---

## 执行模式检测

**⚠️ 重要：根据调用场景自动选择执行模式**

此技能有两种执行模式，在 Step 0 自动检测：

| 模式 | 检测条件 | 执行特点 |
|------|----------|----------|
| **独立调用模式** | 不存在 `DOCS/{需求号}/sched_log.md` | 输出完整报告 |
| **静默返回模式** | 存在 `worktree-{需求号}/DOCS/{需求号}/sched_log.md` | 只更新索引文件，不输出报告 |

### 静默返回模式说明

当作为 ai-auto-dev 的子Agent被调用时：
- 主调度通过 Agent 工具启动子Agent，子Agent自主读取此技能文件并执行
- 完成后**不输出任何状态报告或总结**
- 只更新 `worktree-{需求号}/DOCS/{需求号}/Git提交/exec_prog.md`
- 只更新 `worktree-{需求号}/DOCS/{需求号}/sched_log.md` Step 6 状态
- **直接返回，让主调度自动继续执行后续步骤**

| 禁止输出 | 原因 |
|----------|------|
| ❌ 完整报告框 | 会干扰主调度自动流程 |
| ❌ "推送成功"总结 | 会被误识别为流程终点 |
| ❌ "下一步建议" | 会触发用户交互 |

---

## 执行原则

技能按固定顺序自动执行，无需用户干预：
- Step 0 → Step 1 → Step 2 → Step 3 → Step 4 → Step 5 → Step 6 → Step 7 → Step 8

**自动化原则**：
- 准入检查失败时提示"前置步骤未完成，不具备提交代码的条件"并退出
- 有修改时自动提交，无需选择
- 自动生成commit message并提交
- 自动推送至远程仓库
- 推送成功后自动更新子任务状态（所有子任务→已关闭）
- 所有子任务已关闭后自动更新需求状态

---

## Step 0: 项目检测与模式判断

检测当前目录是否为 git 仓库，自动识别操作范围。

**模式判断**：
- 从分支名提取需求号（格式：`feature/{需求号}` 或类似）
- 检查 `worktree-{需求号}/DOCS/{需求号}/sched_log.md` 是否存在
- 存在 → 静默返回模式
- 不存在 → 独立调用模式

---

## Step 1: 准入检查

从分支名提取需求号，检查 `worktree-{需求号}/DOCS/{需求号}/sched_log.md` 所有步骤状态为"成功"。

**失败时**：提示"前置步骤未完成，不具备提交代码的条件"，显示未完成步骤列表，退出流程。

---

## Step 2: 工作区检查

```bash
git status --porcelain
```

- 干净 → 跳过提交，进入 Step 6
- 有修改 → 自动进入 Step 3 提交

---

## Step 3: 自动提交代码

### 3.1 显示变更

列出修改文件及变更行数。

### 3.2 获取需求下所有子任务ID

**⚠️ 重要：为确保管理部门能准确统计研发工作量，提交时必须关联需求号及其所有子任务ID**

调用 ai-tfs-integration 技能获取需求下的子任务列表：

```bash
# 获取需求下的子任务列表
node .claude/skills/ai-tfs-integration/tools/get-workitem-relations.mjs <需求号> children
```

解析返回结果，提取：
- 需求号（父工作项ID）
- 所有子任务ID列表

**子任务ID提取示例**：
```
需求号: 1626549
子任务列表: 1626592, 1626593
工作项ID集合: 1626549, 1626592, 1626593
```

### 3.3 自动生成 message（包含所有工作项ID）

从分支名提取工作项ID，结合子任务列表，自动生成 commit message。

**⚠️ Commit Message 格式要求**：

格式：`feat(模块): #需求号 #子任务1 #子任务2 ... 提交说明 [AI-Generated]`

**格式说明**：
- 必须以 `#需求号` 开头，确保需求级别关联
- 随后列出所有 `#子任务ID`，确保每个子任务的代码贡献可追踪
- TFS 会自动识别 commit message 中的 `#ID` 格式并建立关联

**示例**：
```
需求号: 1626549
子任务: 1626592, 1626593

生成的 commit message:
feat(ICIS): #1626549 #1626592 #1626593 实现CSS变量修正功能 [AI-Generated]
```

自动执行提交：
```bash
git add -A
git commit -m "feat(模块): #需求号 #子任务1 #子任务2 ... 提交说明 [AI-Generated]" -m "Co-Authored-By: Claude <noreply@anthropic.com>"
```

### 3.4 子任务获取失败处理

| 结果 | 处理方式 |
|------|----------|
| **获取成功** | ✅ 在 commit message 中包含所有子任务ID |
| **获取失败** | ⚠️ 仅关联需求号，记录警告日志 |
| **无子任务** | ✅ 仅关联需求号（需求可能无子任务） |
| **需求号解析失败** | ❌ 提示用户提供需求号，或跳过关联 |

---

## Step 4: 更新文档

自动写入 `worktree-{需求号}/DOCS/{需求号}/Git提交/exec_prog.md`（追加模式），记录 Commit、消息、变更文件。

详见 `references/output-format.md`。

---

## Step 5: 准出检查

```bash
git log origin/$(git branch --show-current)..HEAD --oneline
```

确认本地提交成功，待推送。

---

## Step 6: 自动推送

### 分支保护检查

禁止推送 master/main/develop/release/hotfix 等保护分支（遇到保护分支时报错退出）。

自动执行推送：
```bash
git push -u origin $(git branch --show-current)
```

### 推送状态检测

推送完成后检测是否成功：
- 成功 → 进入 Step 7 更新子任务状态
- 失败 → 记录失败原因，退出流程（不执行 Step 7 和 Step 8）

---

## Step 7: 更新子任务状态

**⚠️ 此步骤仅在 Step 6 推送成功后执行**

**前置条件**：所有子任务状态必须更新为"已关闭"，才能进入 Step 8 更新需求状态。

### 7.1 提取需求号

从分支名或配置文件提取需求号（格式：`AI/{需求号}` 或 `feature/{需求号}`）。

### 7.2 获取需求下所有子任务

调用 ai-tfs-integration 技能获取需求关联的子任务列表：

```bash
# 获取需求下的子任务列表
node tools/tfs-query.mjs get-children <需求号>
```

解析返回结果，获取每个子任务的：
- 任务ID
- 当前状态
- 初始估计字段值
- 完成日期字段值

### 7.3 子任务状态修改路径

**⚠️ 状态必须严格按以下路径逐步修改，不允许跳步骤**

```
已建仪 → 活动 → 已解决 → 已关闭
```

| 当前状态 | 目标状态 | 操作说明 |
|----------|----------|----------|
| **已建仪** | → 活动 | 直接更新为"活动" |
| **活动** | → 已解决 | 更新为"已解决"，需补充字段（见7.4） |
| **已解决** | → 已关闭 | 直接更新为"已关闭" |
| **已关闭** | - | 已是最终状态，无需操作 |

**状态跳转规则**：
- 如果子任务当前状态为"已建仪"，必须先改为"活动"，再改为"已解决"，最后改为"已关闭"
- 如果子任务当前状态为"活动"，必须先改为"已解决"，再改为"已关闭"
- 如果子任务当前状态为"已解决"，直接改为"已关闭"
- 不允许从"已建仪"直接跳到"已解决"或"已关闭"
- 不允许从"活动"直接跳到"已关闭"

### 7.4 已解决状态字段补充规则

**⚠️ 子任务修改为"已解决"状态时，以下字段必须满足要求**

| 字段 | 要求 | 默认值（当字段为空时） |
|------|------|------------------------|
| **初始估计** | 必填 | 默认填 `1`（小时/天） |
| **完成日期** | 如为空则必填 | 默认填 `当前日期 + 3天` |

**字段补充命令示例**：

```bash
# 更新子任务状态为已解决，并补充字段
node tools/tfs-query.mjs update-task <子任务ID> \
  --state "已解决" \
  --estimate 1 \
  --completed-date "$(date -d '+3 days' +%Y-%m-%d)"
```

### 7.5 子任务状态更新执行逻辑

对每个子任务按以下流程处理：

```
对于每个子任务:
    当前状态 = 查询子任务状态

    如果 当前状态 == "已关闭":
        跳过此子任务
        继续

    如果 当前状态 == "已建仪":
        1. 更新为"活动"
        2. 更新为"已解决"（补充字段：初始估计=1，完成日期=当前日期+3）
        3. 更新为"已关闭"

    如果 当前状态 == "活动":
        1. 更新为"已解决"（补充字段：初始估计=1，完成日期=当前日期+3）
        2. 更新为"已关闭"

    如果 当前状态 == "已解决":
        1. 更新为"已关闭"
```

### 7.6 状态更新命令

调用 ai-tfs-integration 技能更新子任务状态：

```bash
# 步骤1: 更新状态（不涉及字段补充）
node tools/tfs-query.mjs update-task-state <子任务ID> "<目标状态>"

# 步骤2: 更新为已解决状态（需补充字段）
node tools/tfs-query.mjs update-task <子任务ID> \
  --state "已解决" \
  --estimate <初始估计值或1> \
  --completed-date <完成日期或当前日期+3>
```

### 7.7 子任务状态更新结果处理

| 结果 | 处理方式 |
|------|----------|
| **单个子任务更新成功** | ✅ 继续处理下一个子任务 |
| **单个子任务更新失败** | ❌ 记录失败原因，继续处理其他子任务（不中断流程） |
| **所有子任务都已关闭** | ✅ 进入 Step 8 更新需求状态 |
| **存在未关闭的子任务** | ❌ 记录失败原因，等待人工处理，不执行 Step 8 |

### 7.8 更新过程文档

在 `worktree-{需求号}/DOCS/{需求号}/Git提交/exec_prog.md` 中追加子任务状态更新记录：

```markdown
### 子任务状态更新
- **需求号**: [需求号]
- **子任务总数**: [数量]
- **已关闭数量**: [数量]
- **更新时间**: [时间]

#### 子任务处理详情
| 子任务ID | 初始状态 | 最终状态 | 更新路径 | 结果 |
|----------|----------|----------|----------|------|
| [ID1] | [状态] | 已关闭 | [状态路径] | ✅ 成功 / ❌ 失败 |
| [ID2] | [状态] | 已关闭 | [状态路径] | ✅ 成功 / ❌ 失败 |
...

**失败详情**（如有）:
- 子任务 [ID]: [失败原因]
```

## Step 8: 更新需求状态

**⚠️ 此步骤仅在 Step 7 所有子任务状态更新为"已关闭"后执行**

### 8.1 查询当前需求状态

调用 ai-tfs-integration 技能查询需求状态：

```bash
# 查询需求状态
node tools/tfs-query.mjs get <需求号>
```

解析返回结果中的状态字段。

### 8.2 状态判断逻辑

| 当前状态 | 处理方式 |
|----------|----------|
| **已分析** | ✅ 继续执行 Step 8.3，更新状态为"已解决" |
| **活动** | ❌ 记录失败原因："需求状态为'活动'，需先完成需求分析"，等待人工处理 |
| **已解决** | ⚠️ 状态已是"已解决"，记录日志，跳过更新 |
| **已关闭** | ❌ 记录失败原因："需求已关闭"，等待人工处理 |
| **其他状态** | ❌ 记录失败原因，等待人工处理 |

### 8.3 更新需求状态（仅当状态为"已分析"）

当需求状态为"已分析"时，调用 ai-tfs-integration 技能更新状态：

```bash
# 更新需求状态为"已解决"
node tools/tfs-query.mjs update-state <需求号> "已解决" "代码已推送，需求开发完成"
```

### 8.4 状态更新结果处理

| 结果 | 处理方式 |
|------|----------|
| **更新成功** | ✅ 记录成功状态，继续执行 |
| **更新失败** | ❌ 记录失败原因（网络错误、权限问题等），等待人工处理 |
| **需求不存在** | ❌ 记录失败原因，提示"需求号不存在于TFS"，等待人工处理 |

### 8.5 更新过程文档

在 `worktree-{需求号}/DOCS/{需求号}/Git提交/exec_prog.md` 中追加需求状态更新记录：

```markdown
### 需求状态更新
- **需求号**: [需求号]
- **更新前状态**: [查询到的状态]
- **更新后状态**: 已解决 / 未更新
- **更新时间**: [时间]
- **结果**: ✅ 成功 / ⚠️ 跳过 / ❌ 失败
- **失败原因**: [如有失败，记录原因：如"需求状态为'活动'，需先完成需求分析"]
```

## 完成后的输出处理

**⚠️ 根据执行模式选择输出方式**

### 静默返回模式（被 ai-auto-dev 调用）

完成以下动作后**直接返回，不输出任何报告**：

1. 更新 `worktree-{需求号}/DOCS/{需求号}/Git提交/exec_prog.md` 状态为"成功"
2. 更新 `worktree-{需求号}/DOCS/{需求号}/sched_log.md` Step 6 状态：

```markdown
### Step 6: Git提交
- **状态**：success
- **调度方式**：Skill调用
- **完成时间**：{时间}
- **Commit ID**：{commit_hash}
- **推送状态**：已推送
- **子任务状态更新**：全部已关闭 / 部分失败（详情）
- **需求状态更新**：已解决 / 未更新（原因）
```

**返回后主调度自动继续执行后续步骤，无需任何信号。**

### 独立调用模式（用户直接调用）

推送成功后输出完整报告，提示下一步操作。

报告格式详见 `references/output-format.md`。

## 完成索引记录（静默返回机制总结）

**⚠️ 重要变更：被调用时不输出状态报告，只做索引记录**

为避免干扰主调度流程，作为子技能完成后**静默返回**：

### 模式检测流程

```
Step 0 模式检测
    ↓
检查 worktree-{需求号}/DOCS/{需求号}/sched_log.md 是否存在
    ↓
├── 存在 → 静默返回模式 → Step 1-8 执行 → 更新索引文件 → 直接返回
└── 不存在 → 独立调用模式 → Step 1-8 执行 → 输出完整报告
```

## 错误处理与失败记录

| 场景 | 处理方式 |
|------|----------|
| 准入失败 | 提示"前置步骤未完成"，退出流程 |
| 推送失败 | 记录失败原因，不执行 Step 7/8，退出流程 |
| 获取子任务失败 | 记录失败原因（网络/权限），等待人工处理 |
| 子任务状态更新失败（单个） | 记录失败原因，继续处理其他子任务 |
| 存在未关闭子任务 | 不执行 Step 8，记录失败原因，等待人工处理 |
| 需求状态非"已分析" | 记录失败原因到 exec_prog.md（如"需求状态为'活动'，需先完成需求分析"），等待人工处理 |
| TFS 查询失败 | 记录失败原因（网络/权限），等待人工处理 |
| TFS 更新失败 | 记录失败原因，等待人工处理 |
| 需求不存在 | 记录失败原因，提示"需求号不存在于TFS" |
